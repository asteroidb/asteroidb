## 1. 規範原則(台帳 §0 の採用)

> **沈黙は情報ではない。物理時間は「いつ仕事をするか」を決めてよいが、
> 「何が真か・何が安全か」を決めてはならない。**

原則の全体系(P1〜P9 + 補則 G1〜G4、緊張と裁定方針)は `principles.md` が正。
本節はレビューで機械的に適用する判定基準と、例外台帳を定める。

**判定基準**(新規コード・設計レビューで機械的に適用する):

- その wall-clock 値を**別の値に変えたとき、安全性が変わるか?** 変わるなら違反
  (安全性が時間に依存している)。スループット・レイテンシ・リソース使用量だけが
  変わるなら適法(スケジューリング)。
- **応答の不在を根拠に、待つ相手の集合を狭めていないか?** 狭めていれば違反
  (分断環境では沈黙が常態)。集合の変更は明示的操作か、保守方向の自動化
  (追加)のみ。

**例外台帳**(原則と衝突するが意図的に残すもの。追加には本表の更新を必須とする。
ラウンド 2 で **再検討条件** 列を追加した — §7 の cut list が全行に再着火条件を課すのと
対称に、例外にも「不要になる/許容できなくなる」反証可能条件を課す。登録は「登録漏れ」を
防ぐが「登録による無限受容」は防がない、という指摘への構造的対処):

## 2. 現状の帰結(何が壊れているか — 台帳 §1 の確定)

certified の証明書が実際に主張しているのは
**「この区画の権威名簿の過半数が、このポリシー版のもとで、このチェックポイント
(1 秒グリッド)に署名した」**だけである。

- フロンティア報告値はデータと無関係に前進する(時計読み値)→ 「過半数の frontier が
  書込 ts を超えた」=「過半数の時計が経過した」。
- 証明書署名は digest を含まない → 報告署名の内容束縛は equivocation 検知にしか
  効いていない。
- 値は複製されない(D2)、status はキー名引きで値と突き合わない(D3)。

さらにこの構造は台帳 §5 の丸め負債(二重述語、バケット攻撃面と上限群、
checkpoint 遅延、つまみの結合、後追い証明書埋め機構)を**すべて自分で生んでいる**。
docs の文言修正(到達性証明への限定)は正直化ではあるが、未踏提案・requirements の
中核主張(「取り込んだ更新の到達境界」「過半数が受信・適用済み」)を満たさない。
**修正すべきは文言ではなく意味論である。**

## 3. 中核再設計: coverage 証明(証明意味論の再接地)

### 3.1 新しい意味論

書込 w の識別を(origin ノード o、その書込に writer が発行した HLC t、キー w.key)とする。

> **certified(w) ⟺ 書込 w の ack 時に耐久記録された policy 版(= 原 pin(書込時 pin)
> — §3.3)の権威名簿の過半数の authority a について、a の署名済み報告 r_a が w を
> 「覆う」**
>
> **「r_a が w を覆う」⟺ `r_a.scope ∋ w.key` ∧ `r_a.origins[o] >= t` ∧
> `w.key ∉ r_a.failed_keys`**

「書込時点の版」は願望ではなく**証拠**でなければならない(ラウンド 2 F1)。w と版を
結びつける機構が無いままこの述語を書くと、pin は coordinator の揮発状態に載り、再起動で
全 pending が「現在の」名簿へ再解決されて名簿縮小をまたぐ false Certified の穴になる
(certified.rs:402-436 の `resolve_scope` 再解決がまさにその形)。束縛の実体
(ack 時の耐久記録・proof への自己運搬・検証の限定)は §3.3 が定める。§3.3 手順 5 は
本述語(ack 時版 = 原 pin 版名簿の過半数)に加え、forward re-pin 後の**現 pin 版名簿の
過半数**という over-covering 方向の追加条件を課す(二重定足数 — 収束ラウンド 2 C1。
forward re-pin 下でも本述語の分母は ack 時版のまま変わらない)。scope 条項は
報告の署名済み range が w.key を含むことの検査であり、別 range の報告の流用を閉じる
(ラウンド 2 F2 — §3.2/§3.3)。

`applied_origins` は既存のセッション保証の per-origin applied frontier である。
その不変条件は「origin o の HLC ≤ h の全書込の効果を含む(または支配する CRDT 状態)—
**ただし `merge_failed_keys` のキーを除く**」(kv.rs:175-182)。この但し書きは飾りでは
なく意味論の一部であり、セッション側の全消費者が実装している(`is_satisfied` は
`merge_failed_contains` を先に引く — session.rs:320-327、`applied_origin_covers` は
`recovery_gaps` を検査する — kv.rs:1341-1353)。claims 転送も「applied frontier と
poison 集合は決して分離できない(分離すれば false success)」を単一 WAL レコード規律で
守っている(eventual.rs:720-729 / wal.rs:122-128)。

**coverage 証明はこの既存規律の報告面への昇格である**(P9: 新しい格子は作らない —
そして再利用は但し書きごと持ってくるのが完全形)。除外情報を落とした frontier を第三者へ
送るのは圧縮ではなく捏造(P3)であり、報告は必ず poison 集合・recovery gap クランプと
一体で生成される(§3.2 の報告生成規律)。

この系で唯一スカラー壁時計だったフロンティアを、既に 3 箇所(dot / floor /
セッショントークン)で使われている per-origin 語彙に揃える(台帳 §2.2 の逆転の解消)。

性質:

- **データ依存**: applied_origins は完全転送の証拠でのみ前進する。時計経過では
  1 ミリも動かない。
- **落とす向きが保守側**: 前進しない誤り(false Pending)はあっても、持っていないのに
  持っていると言う誤りは、**§3.2 の報告生成規律(生成原子性 0・gap/耐久クランプ 1-2・
  failed_keys 同梱 3・claim 採用の送信側 qualifier 4)が守られる限り**構造的に無い
  (台帳 §2.1 の解消)。この条件付けは重要である — 規律のどれか一つ(たとえば poison の
  別便化、あるいは採用経路の qualifier 欠落 — ラウンド 3 F2)を落とすと false Certified の
  穴が開く。条件集合は報告の**生成側**だけでは閉じない: applied_origins は claim 採用で
  他ノードから輸入されるため、採用側の規律 4 まで含めて初めて排除主張が成立する。
- **兼務の解消**(台帳 §2.0): 証明の仕事は「特定の 1 書込 (o,t,key) が覆われているか」
  であり、per-origin 位置の点比較 + poison 除外で足りる — 全体要約(スカラー)は不要。
  要約を必要とするのは GC 側だけになり、そちらは**第三者への証明可能性(証明書への
  組み込み)**を要しない(§3.5。ただし受信時の署名検証は要る — 破壊ゲートの証拠汚染
  防止、§3.2 GC レーン。ラウンド 3 m1)。⚔T2 の単一パラメータ結合が外れる。
- 範囲外の書込まで含意する(applied_origins は store 全体の不変条件)が、
  これは保守方向の過剰であり健全(範囲別に弱める最適化は不要)。

### 3.2 報告 — 生成規律・形・レーン

報告は「scope ごとの時計値」から「**authority の per-origin applied frontier の
署名付きスナップショット + 除外情報 + store root digest**」に変わる。

**形**(ラウンド 2 F2 で scope を署名対象に復元 — **1 報告 = 1 scope** に確定):

```
{ authority, scope: key_range, origins: {origin → hlc},
  failed_keys: [key…],   // = merge_failed_keys ∩ scope(+ 超過時の prefix バケット要約)
  digest, report_hlc,
  policy_version,        // 単数 — 当該 scope の版
  roster_hash }          // 当該 scope の名簿のコミットメント
```

- **scope は署名被覆に含める**。現行の報告署名は既に key_range.prefix を覆っており
  (frontier_sig.rs:77)、初版の列挙はこれを黙って落とす退行だった(訂正)。scope の
  署名被覆がないと、failed_keys 射影が空の別 range の報告を w の証明に流用でき
  poison 除外が無効化され、別 range の小さい名簿を分母に据えた proof が通る。
  FrontierScope(ack_frontier.rs:44-63)の既存規律の踏襲であり新機構ゼロ(P9)。
- policy_versions(複数形)と per-scope 射影の不整合は「1 報告 = 1 scope」で解消。
  複数 scope 構成では scope ごとに報告を発行する(applied_origins map の重複送信は
  帯域見積・scope 共通部一括送信の項で扱う — 下記)。

**報告生成規律**(false Certified の構造的排除はこの 5 点 — 生成原子性 0・クランプ 1-2・
同梱 3・採用側 qualifier 4 — に載る。§3.1)。**適用主語は全報告送信者(名簿 ∪ roster —
本節レーン項)である(収束ラウンド 2 M3)**: R3-F9 が配送規律を全送信者に一般化した
のと対称に、生成規律 0-4・耐久クランプ・report_hlc の M-12 床も非 authority roster
送信者の報告に適用する。初出の主語(「authority の per-origin applied frontier」)の
ままでは適用可否が未規定で、適用すれば下記規律 2 の活性の崖、不適用なら耐久性を過大
主張する報告で GC floor が前進する(G1)— どちらに転んでも欠陥だった。M-12 床の
fsync 永続化は persistence 有効が前提であり、下記規律 2 の構成拒否拡張がその前提を
roster データノード全体に保証する:

0. **生成原子性(ラウンド 3 m2)**: 報告の全フィールド(origins / failed_keys / digest)は
   store の**単一原子スナップショット(同一ロック区間)**から導出する。分割読み取りを
   許す実装は **origins を先・failed_keys を後**に読む順序を必須とし、テストでピンする。
   逆順(failed_keys 先)は、間に claims 採用(adopt_session_claims は origins 前進と
   poison 拡張を同一呼び出しで行う — eventual.rs:729-748)が割り込むと、採用で前進した
   origins と採用前の failed_keys が同一署名メッセージに載り、poison キーへの書込が
   覆われる(false Certified)。origins 先読みなら failed_keys は superset になり
   安全方向 — 規律 1-3 が守られても読み取り順 1 つで崩れる種類の条件は、設計文書に
   明記しないと実装で落ちる(D5 型)。
1. **gap クランプ**: 各 origin o の報告値は、o の open recovery gap がある場合その
   floor 以下にクランプする(`applied_origin_covers`(kv.rs:1341-1353)の報告版)。
   耐久性喪失リスタート後の authority が失われた区間を「適用済み」と署名報告する穴を
   閉じる。クランプは false-Pending 方向のみ。
2. **耐久クランプ**: 報告値は **fsync 済み WAL 適用位置以下**にクランプする
   (M-16 durability ack と同じ根拠)。WAL sync `interval`/`off` の authority は
   fsync 済みの位置までしか報告しない。これにより「過半数が受信・適用済み」という
   証明書の主張は「クラッシュしても失われない」まで含意する — 発行済み証明書が
   authority クラッシュで事後的に少数派保持へ退行する穴(D9 倒立の証明面への再演)を
   閉じる。sync `always` では applied_origins と一致し、`interval` では報告が最大
   sync 間隔ぶん遅れる(false-Pending 方向の対価として受容し、遅延特性 §3.4 に計上)。
   **`off` の帰結(ラウンド 2 F8 — 初版は off を併記しながらコストを計上していなかった)**:
   SyncPolicy::Off は明示 fsync を一切行わず(wal.rs:527 / flusher 即 return :534)、
   durable 水位はセグメント seal(rotate 時の sync_all — :418-441)でのみ前進する。
   つまり off の authority の報告前進は rotate 粒度 = min(セグメント充填, checkpoint
   周期)であり、checkpoint 無効化時は**時間無際限**に遅れる — 低トラフィックでは
   certify がセグメント充填周期に律速され、§3.5 の全量ゲートでは off ノード 1 台が GC を
   無際限に遅らせる。設定 1 行の活性の崖なので設計で塞ぐ:
   **GC ゲート母集合に入る全データノード — 名簿掲載ノード、および roster にデータ
   ノード宣言する全ノード — では sync=off および persistence 無効を構成検証で拒否する**
   (既存の WARN 経路の拡張 + §5.1 admission ハンドシェイクでの耐久構成の宣言・検証で
   足りる — P9。報告 cadence 同期の強制 fsync 案は
   「checkpoint rotate の偶発的 fsync を設計契約に昇格させ結合のピンテストを要求する」
   ため劣後と裁定)。**拒否対象の拡張(収束ラウンド 2 M3)**: R2-F8 時点の拒否対象は
   「authority ロール」限定だったが、全量ゲートの母集合の 名簿 ∪ roster 拡張(R1-F2)と
   報告送り手の非 authority 拡張(R3-F9)の後も構成拒否だけが追随していなかった —
   非 authority roster ノード 1 台の sync=off(合法構成)で耐久クランプ済み報告が
   rotate 粒度でしか前進せずクラスタ全体の tombstone GC が無際限に遅延し、persistence
   無効なら fsync 済み位置が存在せず GC は恒久停止、解除手段は健全稼働ノードへの
   decommission(損失宣告)しかない — §5.1/§3.2 自身が明文で塞いだ誤誘導経路の再生産
   だった(T1/P7 — R2-F8 自身が立てた「活性の崖は設計で塞ぐ」基準の自己適用)。
   sync=interval の非 authority roster ノードの報告遅延(≤ sync 間隔)は GC 遅延特性
   として §12 NFR-002 に計上する。§3.4 の遅延式に耐久クランプ項(sync ポリシー別)を
   計上し、ops-guide の耐久性保証表を v2 意味論で改訂する(§12)。
3. **failed_keys 同梱**: `merge_failed_keys` のうち報告対象 range に交差する分を報告に
   含め、**同一署名メッセージ内で** origins と分離不能にする(SessionClaims と同一の
   「分離不能」規律 — poison を別便にすると欠落・equivocation で同じ穴が再発する)。
   coverage 判定は per-key 除外(§3.1)であり、authority 単位の全不算入は採らない
   (poison は恒久的なので 1 キーで authority を coverage 分母から永久脱落させるのは
   過剰な可用性損失)。
4. **claim 採用は送信側 qualifier とセットでのみ(ラウンド 3 F2 — critical)**: 規律 1 の
   gap クランプは報告者の**ローカル** recovery_gaps しか見ないが、applied_origins は
   claim 採用(complete / sweep pull)で他ノードから**輸入**される。採用経路が qualifier
   を運ばないと、耐久性喪失リスタートしたノード S(gap 開放、生 map は pre-loss 値の
   まま — kv.rs:212-232)から pull した authority A が失われた区間を覆う
   applied_origins[S] を採用し、A 自身は gap を持たないため規律 1 を素通りして署名報告
   する — 消滅した ack 済み書込が過半数 certify される(D9 の証明面再演を塞いだはずの
   規律 2 の裏口)。現行の sync 応答は生 map をそのまま載せ(handlers.rs:1722, 1785,
   1912, 1994)、受信側の merge_applied_origins は採用値を「完全接頭辞保持の証明」と
   みなして自身の gap を**治癒すらする**(kv.rs:1390-1413 — 多ホップでは汚染が各ホップで
   「正規化」される)。裁定:
   - (i) **sync 応答(complete / delta / sweep)に載せる applied_origins は、送信側で
     自身の open recovery gap によりクランプ済みの値とする**。ワイヤ変更不要・
     false-Pending 方向のみの最小解(P9)。代替案(gap を応答フィールドに併送し受信側
     クランプ)は bincode append-only 制約下のフィールド追加 + 全採用経路の改修を要し
     劣後。
   - (ii) sweep 完了時の claim 採用(§3.8)は、送信側スナップショット S の failed_keys の
     同時採用とセットで行う(claims と poison の「分離不能」規律の採用経路への貫徹 —
     adopt_session_claims の既存規律の踏襲。eventual.rs:729-748)。採用上限は gap
     クランプ済み S。
   - (iii) merge_applied_origins の gap 治癒(「採用値 v はこの store が v までの完全
     接頭辞を保持する証明」— kv.rs:1390-1396 の doc 前提)の健全性は (i) に**依存する**。
     この依存を設計不変条件として明文化する(doc コメントの前提の設計契約化)。
   - (iv) 対価の計上: 送信側クランプは gap 保持中 origin の正当な claim 伝播も止める
     (over-clamp = 安全方向。gap は complete 転送による治癒で有界)— §3.4 の遅延式に
     計上する。
   - §10 旧未決点 3(tainted frontier)は「session 側の残債の可能性・別途検証」ではなく
     coverage 中核述語の false Certified チャネルそのものだった — 未決点から本規律へ
     **格上げ**する。受け入れテストは §9(d)。

failed_keys の帰結として明記するもの:

- **poison は恒久かつ伝染性である**(ラウンド 2 F5 — 初版の「修復経路(complete/full
  sync による poison 解消の既存経路)」の記述は**撤回**する。そのような経路は存在しない:
  merge_failed_keys から要素を除去するコードは皆無で「permanently poisoned」が仕様
  (kv.rs:183-191)、claims adoption はむしろ送信側の poison を受信側へ**拡張伝播**する
  (eventual.rs:740 merge_failed_extend、node_runner.rs:4116-4158 apply_complete_state +
  伝染をピンするテスト :7676-7732)。complete sync がデータを完全修復しても poison
  ビットは残る)。帰結: **名簿過半数が同一キーを poison した場合、そのキーの certify は
  恒久 false-Pending で停滞する** — 過少主張なので P3 適合。`principles.md` 緊張表 T9
  (ラウンド 3 m6 で §1 台帳から移管)と NFR に正直に計上し、P7 に従い counter +
  スロットル WARN で可観測化する。ops-guide には**回避策**(当該キーの作り直し・
  型統一後の新キーへの移行)を記載する(§12)。
  証拠ベースの un-poison は「既存経路の流用」では成立しない — 現行 poison はどの寄与
  (origin/HLC)を落としたかを記録しないキー単位ビットのため、落とした寄与の出所を
  SessionClaims と同一レコードで記録する新しい証拠機構が要る。P9 に従い実需(T9 の
  再検討条件)が出るまで作らず、§10 に将来オプションとして登録する。
  **GC 側帰結(ラウンド 3 F5 — certify 側と別軸の恒久コスト)**: poison の恒久性・
  伝染性と §3.5 の failed_keys ゲート検査の合成により、poison キーの remove の mark は
  全 authority のゲートを恒久に通れず、当該キーの tombstone は**恒久収集不能・無際限
  蓄積**になる。この資源圧は §5.1 の「決断期限は資源圧」裁定で解消できない — 阻止して
  いるのはノードでなくキー単位の恒久ビットなので、decommission にも re-admit にも
  対応する運用操作が無い「**決断不能な資源圧**」である。§5.1 の資源圧メトリクスで
  poison 起因分を分離表示し(decommission 判断への誤誘導防止)、回避策の実行時
  **旧キーの delete はまさに収集不能な remove を 1 キー分残す**こと(残置か delete かの
  トレードオフ)を ops-guide に明記する(§12)。退避側の設計方向(全員一致の放棄証拠に
  よる key 単位隔離)は §10-10。ゲート不成立の粒度は当該キーの mark に限定する(§3.5 —
  poison 1 キーで全 GC を止めない)。
- **サイズ有界化は保留(崖)でなく安全方向への段階縮退(坂)**(ラウンド 2 F7 —
  初版の「上限超過時は該当 range の coverage 報告を保留」は**撤回**する。それは同じ節が
  「1 キーで authority を coverage 分母から永久脱落させるのは過剰な可用性損失」として
  棄却した authority 単位全不算入を、サイズ上限の裏口から崖付きで再導入していた。
  poison は恒久・発生源は相関的(不良デプロイ、wal.rs replay の型不一致 poison)なので
  複数 authority の同時閾値超過は現実的シナリオである)。改訂: failed_keys の range
  射影が上限を超えたら、**超過分を prefix バケット単位の「このサブ range は全キー除外」
  マーカーに要約**し、origins と同一署名メッセージ内に収める(分離不能規律維持・
  全量集合上で評価可能なので差分報告制約とも両立)。authority の coverage 寄与は
  バケット外の健全キーに対して生存し、崖が坂になる(全バケット poison 時のみ従来の
  保留と同等に退化)。健全キーの false-Pending 化は over-covering であり安全
  (kv.rs:203-210 の方向規律)。無音 truncate は false Certified の再導入なので禁止。
  閾値決定(§10-1)には「相関 poison の現実的上限(伝染 union 込み)≪ 閾値」の
  論証義務を課す。counter + WARN(kv.rs:1421-1426 の poison WARN 規律と同族)。

**origins は全量必須(間引き禁止)** — §10 旧未決点 1 の確定:

- v2 初版の「上限・間引きはトークンと同じ規律 — 間引きは false-Pending 方向にしか
  効かない」は**削除**する。接地が誤っていた: セッショントークンの間引きは、コード自身が
  LIMITATION と自認する monotonic-reads の実質的弱化(false success 方向への露出)で
  ある(session.rs:37-47)。方向が逆の先例は安全性の根拠に使えない。またトークンの
  64 上限は「ステートレスでサイズ有界なクライアント側トークン」という制約由来であり、
  authority 報告は roster で自然に有界なサーバ間メッセージ — 前提が輸入できない。
- 間引きは certification では静かな origin の恒久 certify 不能(可用性の崖)、GC では
  §3.5 ゲートの恒久不成立(D1 と同型の無音停止)を生む。よって**証明に使う報告は全量
  必須**。ただし超過時の挙動は「counter + WARN 付きの報告失敗」(初版)を**撤回**し、
  **安全方向への段階縮退(坂)**とする(ラウンド 3 F10/m3 — 同一文書内で failed_keys が
  確立した崖→坂裁定(R2-F7)と同型の失敗形状に非対称な裁定を併存させない。報告全体の
  失敗は当該 authority を certify 分母と GC 報告から丸ごと消し、origins は累積単調・
  引退は二重ゲートなので閾値到達は不可逆 = 到達した瞬間 certify と GC が同時恒久停止
  する崖だった): 明示閾値を超えたら **roster 現役 origin を優先し、超過分の非 roster /
  引退候補 origin を counter + スロットル WARN 付きで報告から欠落させる**。欠落は
  under-covering(当該 origin の書込が false-Pending、当該 origin が remover の mark は
  ゲート不成立)で安全方向であり、authority の coverage 寄与と GC 報告は残余 origin に
  ついて生存する。超過の実体は構成異常(短命 writer の累積・引退の不履行)なので、
  欠落 origin の列挙診断を P7 義務とする。
- **有界性の正直な記述(ラウンド 3 F10 — 初版の「origins の定義域は roster 由来であり
  敵対的に膨張しない」は削除する)**: P1 は eventual 書込のローカル受理を無条件とし、
  §5.1 の加入意図フィールドは正当な非 roster writer(意図的短命ノード等)を明示的に
  許す(宣言なし = roster 追加なし・merge 継続)ため、origins の定義域は下記帯域見積 (a)
  のとおり「**歴史上の全 origin の累積**」であり roster では有界化されない。非 roster
  origin は roster decommission の対象になり得ず、下記引退条件 (i) の拡張
  (origin-retire)がなければ永久に引退不能だった。この累積と閾値の存在は
  `principles.md` T3 に計上する。
- プール側の保持「**(scope, authority, roster_hash) ごと**最新 1 件置換」(次元は §3.3
  裁定 2 が正 — 収束ラウンド 2 M5 で本行にも明記)の正当化条件は「**新報告の origin
  定義域が旧報告を包含する**」こと(**同一 roster_hash 内でのみ**適用 — §3.3 裁定 2)。**この包含は段階縮退の非発動時に成立する**(欠けるのは
  引退 origin のみで、引退は下記の証拠ベース規律に従う)。**縮退発動時は欠落した
  非 roster origin の被覆材料が置換で失われ得る**(under-covering で安全方向だが、
  「常に成立」を不変条件として assert する実装は不可 — 収束ラウンド 1 m3: R3-F10 の
  段階縮退導入で初版の無条件成立は偽になった。成立しなくなった不変条件を根拠として
  引用し続けない — R3-F8 と同型の訂正)。

**report_hlc(equivocation 識別子)— report_seq は不採用**:

- 初版の `report_seq`(authority ローカル単調カウンタ)は**採用しない**。再起動・
  バックアップ復元を跨いだ単調性の設計がなく、M-12 が frontier report HLC で塞いだ
  自己冤罪穴(壁時計ロールバックで正直なノードが「完全に有効に見える equivocation
  ペア」を自作する — report_clock.rs:4-10)をカウンタで再導入することになる。塞ぐには
  M-12 一式(write-ahead lease 床の fsync 永続化 / 床欠如時の activation grace /
  backup 復元禁止の ops 規則)の複製が必要で、床付き厳密単調な報告識別子が既に系内に
  あるのに新しいカウンタと永続化義務を増やすのは P9 違反。
- 新報告は **M-12 ReportClockFloor で覆われた丸め無しの report HLC** をフィールドとして
  持ち、equivocation の識別を「同一 `(authority, scope, report_hlc)` で内容が異なる」と
  定義する(1 報告 = 1 scope なので識別子にも scope が要る — ラウンド 2 F2 の帰結)。
  検知は現行も丸め前の report HLC で行われており(equivocation.rs:3-5)、§3.3 で
  グリッドを削除しても識別子はそのまま使える(初版が動機とした「frontier_hlc 同一性 =
  丸めの副産物」は不正確だった)。HLC を**一意性トークン**として使うのは P5 適法 —
  安全性は「署名済み識別子を再利用しない」に載り、それは M-12 の床が保証する。
- 識別子が再利用不能なので、観測保持の「authority ごと最新 K 件」への件数ベース化
  (§4)はそのまま安全に採用できる。

**レーンと配布(cadence / fanout の分離)** — §2.0 の兼務解消を配布面まで貫徹する:

- 報告の**形式は一本**(上記。二つのフォーマットは作らない — P9)だが、配布は
  2 レーンに分ける:
  - **certify レーン**: 署名付き全量報告を **authority 名簿・certification 消費者向け**に
    配布する。cadence は「高頻度(現行 frontier_report_interval 相当)」を天井とするが、
    実際の既定値は**下記「報告配送の規律」の帯域制約(報告サイズ × 配送タイムアウトの
    整合、帯域予算上限割合)に従属**する(ラウンド 2 F9 — 初版の「毎秒相当」は報告が
    O(累積 origins) に成長した後は配送可能性と矛盾し得る。§10-7)。
  - **GC レーン**: 同じ per-origin ベクトルを**低頻度**で配布する。送り手は
    **名簿 ∪ roster の全ノード**(§3.5 の全量ゲートの入力 — authority に限らない)、
    受け手は GC ゲートを評価する全 peer。配送は certify レーンと**同一の配送規律**
    (下記 — resumable / サイズ×タイムアウト整合 / counter + WARN)に従う(ラウンド 3
    F9 — 初版の「頻度だけが落ちる」は**撤回**する: 低頻度化はメッセージサイズ対
    タイムアウトの比を一切変えず、現行トランスポート(全体 5 秒・分割不能・失敗は
    debug のみ)の継承では、報告が帯域 × 5 秒を超えた roster ノードが 1 台でも
    あれば — そのノードが健在で送信を試み続けていても — 報告はどこにも着地せず、
    全量 fail-closed の GC ゲートがクラスタ全体で恒久停止する)。GC ゲート(§3.5)が
    要しないのは**第三者への証明可能性(証明書への組み込み)**であって受信検証では
    ない — **ゲート評価に供する報告は受信時に署名検証に合格したもののみ**とする
    (ラウンド 3 m1: decode fail-open が push 証跡を汚染した前例(台帳 §7)のとおり、
    CFT でも転送・デコード欠陥は破壊ゲートの証拠を汚染する。P3 は証拠の生産側まで
    貫かないと消費側の fail-closed が無意味 — principles.md P3 緊張の自己適用)。
    **非 authority 送信者の報告の検証鍵の出所(収束ラウンド 1 M6)**: 送り手は
    名簿 ∪ roster の全ノードだが、検証鍵の権威レコード(F12)は authority 名簿レコード
    のみで、非 authority roster ノードの報告には検証鍵の出所が無かった — 書かれた
    とおり実装すると全量 fail-closed ゲートが恒久不成立(クラスタ全体の GC 恒久停止。
    decommission してもそのノードが母集合から消えるだけで、roster に残る他の非
    authority ノードの報告は依然検証不能 — 運用操作でも解けない D1 型)か、実装者が
    検証を諦めて破壊ゲートの証拠汚染(m1 が塞いだ穴)を再導入するかの二択になる
    (G1/P3 対 T1/P7 の合成矛盾)。裁定: **roster レコードに各ノードの公開鍵を同梱し
    (§5.1 — roster = {node_id → (addr, state, 公開鍵)}、roster 同一性 = (id, 鍵) —
    F12 と同一の G3/R2-M2 論拠 = 検証可能性の時間・評価者不変)、非 authority 送信者の
    報告はこの鍵で受信検証する**。roster は既に Raft 一次データ(§5.1)なので、版付き
    規律・decommissioned 痕跡・admission に鍵登録を載せるだけで新機構最小(P9)。鍵は
    加入意図宣言ハンドシェイクで提出し auto-add の Raft commit に同梱する。名簿掲載
    ノードは名簿レコードの鍵が優先(重複は roster_hash 束縛と整合させる)。roster 鍵の
    変更は F12-2 と同形の失効規律(新版 roster commit + 行き渡り証拠)に従う。棄却
    記録: 代替(admission 時 Raft 登録の node key registry 新設)は名簿鍵と registry の
    二重化で P9 劣後 — F12 縮小案の棄却記録と対称。受け入れ条件は §9(f)。
- 帯域見積の補正: 初版の「クラスタのノード数オーダ」は二重に過小だった。
  (a) origins の定義域は「現行ノード数」でなく**歴史上の全 origin の累積**である
  (applied_origins に削除経路が無い — kv.rs:175-182 の意図的不変条件)。
  (b) 全 peer × 毎秒 fanout ではクラスタ帯域が O(N² × 累積 origins)/秒になる。
  レーン分離後は O(|authorities| × N × 累積 origins)/秒 + 低頻度項。全ノード authority
  構成では N² に退化すること、複数 scope 構成では store 全域の applied_origins map が
  scope 数分重複送信されることも設計制約として明記する(圧縮でなく scope 共通部の
  一括送信で解く — ワイヤ詳細は実装時)。
  (c) **equivocation observed レーンの増幅項(ラウンド 2 F11 — 三重目の過小の訂正)**:
  frontier push には observed レーン(最大 GOSSIP_SAMPLE_MAX = 64 件の
  ObservedAttestation、各件が報告全体 + 署名の完全コピー — equivocation.rs:124,
  132-138)が毎 tick 同乗し(node_runner.rs:2231-2239)、M-14 sync piggyback も同じ
  全文を再配送する。報告が O(累積 origins) に成長すると observed レーンは push 1 回
  あたり最大 **64 × 報告サイズ**(試算 115KB〜1MB)= 報告本体の 64 倍の増幅項になる。
  split-view 検知は署名が報告全内容を覆うことに依存するため、observed レーンだけ報告を
  痩せさせる自由度は現設計に無い — レーン分離では解けない。見積には
  「observed 項(× GOSSIP_SAMPLE_MAX × 報告頻度 × N)+ M-14 piggyback 項(サンプル
  指紋が変わる活動時は実質毎サイクル)」を計上する。
- **observed レーンの二相化(F11 の設計方向)**: observed レーンを
  「`(authority, scope, report_hlc, content_hash)` の要約(署名なし)」に痩せさせ、
  同一識別子でハッシュ相違を検出したときのみ両全文を保持元(relay は検証済み全文を
  保持)からフェッチして証拠化する。検知は識別子 + 内容ハッシュ比較で足り、非否認
  証拠としての全文 2 通は衝突検出後の取得で間に合う — 未検証要約を accusation の
  根拠にせず、フェッチ + 再検証後にのみ evidence 化する(証拠の出所規律に整合)。
  注意 2 点を仕様に含める: 偽ハッシュによる無駄フェッチ DoS に対しフェッチの
  レート上限が必要(スケジューリング、P5 適法)。分断中はフェッチ不能で検知が遅延する
  (false-negative 方向なので許容 — P7 に従い counter で可観測化)。
  GOSSIP_SAMPLE_MAX の件数上限をバイト予算上限に変える見直しを §10 に登録する
  (gossip サンプルの縮小は検知遅延方向にしか効かず安全側 — session token 間引きとは
  方向が違う)。**実装順序の制約**: 実装タスク #7(coverage 証明)で報告を肥大化させる
  前に、この増幅項の手当(最低でも二相化の採否)を確定していなければならない。
  (d) **GC レーンの N×N resumable セッション項(ラウンド 3 F9)**: GC レーンの送り手は
  名簿 ∪ roster の全ノード(**非 authority roster ノードを含む**)なので、配送セッション
  は N×N オーダになる。低頻度 × resumable でも、同時セッション数・再開状態の保持
  コストを帯域・メモリ見積に計上する。再開状態には送信側の耐久化分(報告 1 件分の
  署名済みスナップショットバイト列 + 受信者別カーソル — 下記配送規律、収束ラウンド 2
  M8)を含む。
  (e) **GC レーン受信キャッシュ項(収束ラウンド 1 m4)**: §3.4 の per-origin ピア広告は
  GC レーン報告の受信キャッシュを広告構造として使うため、各ノードが名簿 ∪ roster
  全送信者の最新報告を保持する — per-node **O(|名簿 ∪ roster| × 報告サイズ)**
  (本文書の試算どおり報告が 115KB〜1MB 級へ成長すると数十 MB/ノード規模)。配送状態
  ((d))とは別の保持コストであり、§5.1 の sizing 指針(容量計画式)の入力に含める
  (T3/P8)。
  (f) **供給側の耐久 sweep 状態項(収束ラウンド 2 m4)**: §3.8 の送信側耐久化
  (sweep_id, S, カーソル) の S は applied_origins + failed_keys のスナップショット =
  報告と同一内容クラスであり、**サイズは報告サイズと同階(分断中は同じ成長則に従う)**
  — 初出 M7 の「小さく」は本節の自己計上(試算 115KB〜1MB・分断中無際限成長)と矛盾
  するため撤回する(§3.8)。sweep は claim キャリアの正系として全 authority + 中継が
  周期実行するため、ハブ的供給者は **O(同時 inbound sweep セッション数 × |S|)** を
  並行耐久保持する — §5.1 / §12 の sizing 入力に含める(m4(受信キャッシュ計上漏れ)と
  同型の残漏れの補充)。回収規律は §3.8 再開の規律に定める。

**報告配送の規律(報告配送一般 — 両レーン・全送信者)** — ラウンド 2 F9(critical)を
ラウンド 3 F9 で certify レーン限定から一般化した: §3.8 が pull 側の
原子単位を有界化したのと同じ要件が、証明の土台である報告 push 側にもかかる。現行
トランスポートは全体 5 秒タイムアウト(frontier_sync.rs:69-72, 80-84)・毎 tick 全量
再送・失敗は debug ログのみ(node_runner.rs:2302-2309)であり、報告が「帯域 × 5 秒」を
超えた authority は**永久に配送不能 = coverage 分母から無音で消える**(certify 恒久
false-Pending + §3.5 ゲート恒久不成立)。報告は分割不能な単一署名メッセージ(全量
スナップショットのみ・failed_keys 同梱必須)なので、D6 と同形の livelock を報告レイヤに
新規に作り込むことになる。裁定:

- **報告の配送は専用チャネル**とする(certify レーン・GC レーンとも): 低頻度・大
  タイムアウト・**resumable**(転送の再開可能性はトランスポート層の性質であり、報告
  形式は一本のまま — P9)。**GC レーンの送り手には非 authority roster ノードを含む** —
  「証明書用報告の送り手」に限る読みは成立せず、その配送失敗も下記 P7 義務の対象で
  ある(ラウンド 3 F9 — debug 止まりからの昇格は全送信者に適用)。
  origin サブセット分割署名の代替案は、プール置換健全性(新報告の定義域が旧報告を
  包含する — 上記)とバケット削除根拠に衝突し、プールの (authority, サブセット)
  キー化という複雑性を部分復活させるため**劣後**(採用するなら置換不変条件の再論証が
  必須、と記録する。**再論証条件の注記(収束ラウンド 1 m3)**: 根拠とした置換健全性の
  不変条件は R3-F10 の段階縮退発動時に条件付きになった(上記)— 縮退の常態化が実測
  されたら本劣後判定を再論証する)。
- **再開対象の同一性(収束ラウンド 1 m2)**: 配送セッションは **(report_hlc,
  カーソル)** で識別し、**開始済みセッションは当該スナップショットを完了まで運ぶ —
  送信側の新スナップショット発行(chain 打ち切りの周期全量)はセッションを無効化
  しない**。完了後の鮮度回復は差分報告(delta chain)で行う。自然な実装(接触のたびに
  最新スナップショットへ載せ替え)は、スナップショット周期 < 配送完了時間の環境で
  base 配送が毎回リセットされ永遠に完了しない — R2-F9 が塞いだ「毎 tick 全量再送」
  livelock の resumable 層での再演(D5 型の「設計に書かないと実装で落ちる」条件)。
  origins の累積単調性・failed_keys の単調追加により、旧スナップショットの完遂は
  under-covering 方向で常に安全 — 規律化に安全上の障害はない。§3.8 の (sweep_id,
  カーソル) 再開規律の配送側対称。受け入れテストは §9(f)(配送中のスナップショット
  世代交代下で base 配送が完了する)。
- **配送セッションの送信側耐久化(収束ラウンド 2 M8 — §3.8 M7 の配送側対称)**:
  配送セッション **(report_hlc, 署名済み報告スナップショットのバイト列, カーソル)** は
  送信側で**耐久化**し、クリーン再起動(§3.2 の recovery gap 開放が検知されない再起動)を
  またぐ再開を許す。M7 が sweep 側で明示的に塞いだ「送信側連続稼働時間 ≥ 完了時間」と
  いう未計上前提が、push 側 = 報告配送にそのまま残っていた — 接触窓ごとに電源断・
  再起動するノード(M7 自身が挙げる衛星系の現実の類型)が送信者の場合、再起動のたびに
  セッションが消え新スナップショット発行で base 配送がリセットされ永遠に完了しない
  (上記 m2 が塞いだ「載せ替え」livelock の再起動版。帰結は当該送信者の報告の恒久
  未着 = GC 全量ゲートのクラスタ全体停止 + authority なら certify 分母からの恒久
  欠落)。報告は署名済みなので再署名は不要で、**同一 report_hlc + 同一内容の再送は
  equivocation 定義(「同一識別子で内容が異なる」— 上記)に抵触しない**(この整合を
  明記する)。耐久性喪失リスタートはセッション無効化 + 新スナップショット発行
  (sweep と同じ「精密化であって緩和ではない」構図)。P7 義務: セッション無効化
  再開始 counter。耐久化状態の保持コストは帯域見積 (d) に計上する(実装は報告 1 件分の
  バイト列 + 受信者別カーソルで共有可)。これで §12 NFR-002 行と §3.4/§3.8 の
  「送受信双方のクリーン再起動をまたぐ再開(push/pull 両側)」文言は push 側も設計
  条項に接地する — 収束ラウンド 1 の改訂同士(m2 と M7/§12 補正)の間で、設計本文が
  提供しない保証を requirements に書かせていた矛盾の解消。受け入れテストは §9(f)。
- **P7 義務**: 送信側の配送失敗は counter + スロットル WARN(現行 debug からの昇格 —
  両レーン・全送信者)。消費側にも「送信者 X の報告が stale」の可観測性義務を課す
  (GC 側のゲート阻止理由の可観測化は §3.5、配送レイヤの staleness は本規律が両レーンに
  課す)。per-peer の配送成否・最終成功時刻は提示のみで判定には
  使わない(P5 適法)— §5.1 の decommission 判断支援証拠にも「この authority の報告が
  最後に届いた記録」として供給する。
- **cadence 設計制約**(§10-7 に登録): 「リンク帯域予算に対する報告レーンの上限割合」
  と「報告サイズ × 配送タイムアウトの整合条件」を設計制約とする。
- §3.8 の「coverage 前進の原子単位の有界化は証明意味論の必須要件」宣言は
  **pull(claim 採用)と push(報告配送)の両側**に一般化する。受け入れテストに
  狭帯域・短接触窓での報告配送前進をピンする(§9)。
- **origin 引退規律**(累積成長への証拠ベースの蓋): 引退は**報告からの除去に限定**する。
  store の applied_origins 本体からの削除は、compaction 後の旧セッショントークン充足と
  いう明示不変条件(kv.rs:178-180)を破壊するため**禁止**。引退条件は
  (i) 当該 origin が roster で decommissioned(明示操作の証拠 — §5)**または
  `origin-retire(node_id)` 明示運用操作**(ラウンド 3 F10 — roster に一度も入らない
  正当な writer(§5.1 の宣言なしノード)の origin は roster decommission の対象に
  なり得ないため、roster 非依存の引退経路が必須。decommissioned 集合と同様、明示操作の
  回数で有界。引退候補 = 非 roster origin の列挙は P7 義務として診断に載せる)、かつ
  (ii) 当該 origin の位置が全 authority で合流済み(coverage と同形の証拠)。
  **引退は Raft コミットレコードとし、(ii) の合流位置(全 authority 合流を検証した
  時点の当該 origin の**合流検証時位置** — 単一スカラー)を証拠として同梱する**
  (ラウンド 3 F3 — 引退後にこの origin の remove が mark された場合の §3.5 ゲート
  充足材料。単一スカラーなので、引退後に名簿へ追加された新 authority もこのレコードで
  閉じられる)。時間経過・沈黙は条件にならない(P4)。引退 origin の GC ゲートでの
  扱いは §3.5。
  **引退の意味論 = 合流検証時位置以下の接頭辞のマスク(収束ラウンド 2 M2 — 引退
  origin の再活動の規定)**: 初出の「最終位置」は改称する — レコードが主張する最終性を
  強制する機構は何もなく(merge は止められない — G2)、P1 と §5.1 は引退後の書込継続を
  明示的に許す(re-admit されたノード、復帰した「予定された不在」衛星、非 roster
  writer のローカル受理は無条件)ため、「最終」は将来事実により偽になり得る証拠の
  過大主張だった(G1)。裁定: 報告生成が o を省略してよいのは
  **applied_origins[o] ≤ 引退レコードの合流検証時位置** の間のみ。合流検証時位置を
  超える o の寄与を観測したノードは o を報告へ**自動再掲載**する(追加 = 保守方向
  なので P4 適法)+ counter + スロットル WARN(P7)+ **Raft un-retire レコード**で
  フリート同期する(再掲載の分散知識を各ノードの独立判定に任せない)。段階縮退
  (上記)は再掲載 origin を「引退候補」として再欠落させない — roster 現役と同順位で
  優先する。un-retire 経路が無いままだと、引退済み origin の再活動後の新規書込は恒久
  certify 不能・新規 remove の mark は恒久ゲート不成立(§3.5 の充足二択 — 報告
  エントリは恒久欠落、引退レコードの合流位置 < 新 remove HLC — をどちらも恒久に
  満たせない)となり、正規運用操作(re-admit・衛星復帰)から到達する無音の恒久停止
  だった(D1 型)。runbook への接続(re-admit は un-retire を連鎖必須、origin-retire は
  「恒久宣告ではない」)は §12、活性の受け入れテストは §9(j)。
  **限界の計上(ラウンド 3 m3/m4)**: 条件 (ii) は authority が 1 台でも長期不在なら
  成立しないため、**引退は分断中(= サイズ抑制が最も必要な期間)全 origin について
  停止する** — 「引退が実質のサイズ上限」(§3.3 試算)は平時にのみ機能する上限であり、
  分断が長引くほど報告は成長し、復帰時の配送(下記配送規律)をさらに困難にする
  自己強化ループになる。容量・帯域計画の入力は「最長想定不在 × (tombstone +
  **報告サイズ成長**)」に拡張する(§5.1 / §12)。(ii) を pin 分母と同形の「過半数 +
  残余は floor 沈降待ち」へ弱められるかは §10-13 に登録。
- **差分報告 — ワイヤ形式と署名被覆の決定**(実装は後回しでよいが、決定を先送りすると
  将来もう一度ワイヤ移行 = もう一度混在期 fail-closed を支払うため、ここで確定する):
  - 差分報告(`base_report_hlc` + 変化した origins エントリ + 追加 failed_keys)は
    **GC レーンおよびプール状態の更新にのみ使える**。**証明書に入る報告は全量
    スナップショット報告のみ**(署名被覆 = 全量内容)。理由: coverage 判定の
    `w.key ∉ failed_keys` は全量集合に対してしか評価できず、差分連鎖から再構成した
    集合を署名検証なしで証明書に使うと分離不能規律が崩れる。
  - 全量スナップショットの周期が certify 遅延に入る(§3.4 に計上)。
  - 混在互換: 差分を全量と誤読する旧受信者は under-covering(安全側)に落ちる。
  - **delta chain の具体形式(ラウンド 3 F9 — §10 旧未決点 6 をここで確定。初回・
    分断復帰後の base 配送が短接触窓環境の定常状態である以上、形式未決のままでは
    GC レーンが差分に「逃げられる」保証がない)**:
    (i) 差分は「受信側が保持する**署名検証済み**全量スナップショット(`base_report_hlc`
    で識別)」に対してのみ適用可能。base を保持しない受信者は差分を**破棄し
    (fail-closed)**全量スナップショットを要求する。差分連鎖の再構成集合をゲート評価に
    使ってよいのは、base とすべての中間差分が同一送信者の署名検証に合格した場合のみ。
    (ii) failed_keys / prefix バケット要約は**単調追加のみ**を差分で運べる(poison は
    恒久なので縮小方向の差分は形として存在しない)。
    (iii) 送信側は周期的に全量スナップショットを発行して chain を打ち切る(chain 長は
    有界 — スケジューリング、P5 適法)。**初回・分断復帰後の base 全量スナップショット
    配送には上記配送規律と同じ再開可能性要件がかかる** — ここが resumable でなければ
    差分報告の存在意義自体が消える。

**混在期(旧報告形式との共存)**:

- 旧報告(時計 basis)と新報告(coverage basis)の区別は新フィールドの有無そのもの。
  **混在期、旧形式の報告は coverage に数えない(fail-closed)**。
- 再開条件の正確な記述(初版の「全 authority が更新されるまで保留」は過大で誤り —
  coverage 述語(§3.1)は名簿の**過半数**で成立する):
  **当該 range の名簿の過半数が新形式で報告し、その報告が書込を覆った時点で、その
  range の新規 certify は再開する**。certification は per-range 名簿
  (ack_frontier.rs:487-500 majority_frontier_for_scope の per-scope 閾値)なので、
  混在期の停止は range 単位で解除できる。
- ローリング手順(ops-guide に明記 — §12): range ごとに名簿過半数を先に揃える
  アップグレード順序を推奨し、観測は「区画別の新形式報告数 counter」で行う。
  分断常態のフリートでは到達不能な authority を待たずに多数派側の更新完了で range 単位に
  再開できる — これが §10 旧未決点 2(レガシー明示フラグ案)より先に効く実質的緩和で
  ある。
- **混在期の GC 側裁定(ラウンド 2 F6 — 初版は certify レーンしか手当てしていなかった)**:
  §3.5 の authority ゲートは母集合(名簿 ∪ roster)の**全量** per-origin 報告を要求し
  欠落は fail-closed なので、旧形式ノード(origins map を持たない報告)が 1 台でも残る間、
  **tombstone GC はクラスタ全体で停止する**。分断常態のフリートでは到達不能ノードの
  アップグレードは接触時にしか起きず、この停止は無際限になり得る — 明示的コストとして
  計上する:
  - **GC 再開条件 = 名簿 ∪ roster の全ノードが新形式報告に到達**。アップグレード順序
    仕様に含める(certify の range 別 counter とは別物)。
  - **可観測化**: 「GC ゲートを塞いでいる旧形式ノードの列挙 + 停止中 tombstone 蓄積
    レート」を §5.1 の資源圧メトリクス(gc_gate_diagnose 拡張 — P9)に載せる。
  - **部分緩和(健全性論証付き)**: peer ゲートの push 証跡(node_runner.rs:3443-3452、
    ゼロエラー完遂 push = mark 済み tombstone を含む全状態の merge 証明)は報告形式と
    独立な転送証拠であり、crdt/gc.rs:33-38 の安全基準「all known replicas have already
    incorporated the remove」を旧ノードについて**直接証明できる**。よって**直接 push
    相手である旧形式ノードに限り**、per-origin 報告の代替として push 証跡でゲートを
    通過させてよい(証拠の出所規律に適合)。ただし直接 push 相手にしか証跡が無いため
    多ホップ先の roster メンバーには効かず、残りは上記の停止受容と可観測化で扱う。
  - **運用注記**(§12 ops-guide / §5.1 判断支援証拠): **旧ソフトノードの正しい救済は
    decommission ではなくアップグレード**である。資源圧メトリクスが「まだ旧ソフトを
    走らせているだけの健全ノード」への損失宣告に運用者を誤誘導する経路を明文で塞ぐ。
  - §10 旧未決点 2(レガシー明示フラグ案)の「必要性が下がった見込み」は certify のみの
    推論だった — GC 側の停止コストを根拠に**再評価を前倒し**する(§10)。
- ワイヤは既存 FrontierPushRequest への **append-only フィールド追加 + serde(default)**
  で運べる(実績ある機構)。新フレーミングは不要 — これが v1 A3 Stage 1-3 を
  カットできる根拠でもある(§7。ただし §3.8 の DeltaSyncRequest 拡張を試金石として
  再着火条件に登録)。**「実績ある機構」の実績の中身を正直に引用する(ラウンド 2 M5)**:
  救済の実体は send_with_json_fallback(frontier_sync.rs:132-159)の
  「全量 bincode 送信 → 受信側拒否 → 同一データを全量 JSON 再送信」= **二重送信**であり、
  失敗検出は全ボディ送信完了後にしか起きない。混在期は旧 peer あたり報告サイズ ×
  2〜3 × cadence の上り帯域(衛星リンクで最も希少な方向)を消費し、上記 F9 の配送
  タイムアウトと相互作用する(bincode 送信でタイムアウトを消費すると JSON 再送も失敗)。
  緩和として新形式送信前の**能力プローブ**(既存の digest 非対応キャッシュ TTL と同族の
  スケジューリング — §1 で適法分類済み)を許容し、§7 A3 試金石の測定項目に
  「上り帯域の二重送信税(タイムアウト相互作用込み)」を明記する。

### 3.3 証明書 = 報告署名の集合(グリッドとバケットの削除、名簿の pin)

報告署名は**すでに報告の全内容(scope / origins / failed_keys / digest / report_hlc /
policy_version / roster_hash — §3.2 の形)を覆っている**(scope の被覆は現行
frontier_sig.rs:77 の踏襲 — ラウンド 2 F2)。証明書はこれを使う:

> **certificate(w) = { (report_a, sig_a) : a ∈ 名簿(w), report_a が w を覆う(§3.1)}
> が 名簿(w) の過半数に達した集合**

**名簿の pin(検証の分母を評価時点から切り離す)**:

- **名簿を合意済み・版付きの一次データに昇格する**: 現在、自動生成 authority・版履歴・
  namespace 版はノード局所の導出値で複製されない(台帳 §4.5)。v2 では authority 名簿の
  変更(自動再計算の結果を含む)を **Raft コミット対象**とし、変更ごとに policy_version
  (または名簿専用版)を必ず bump、歴史的名簿を複製コアに保持する。これは §6「合意が
  必要なのは roster と policy/authority 定義」の帰結であり、certification の**分母**は
  「信頼の根は液性ドメインに追従させない」(P4 系)が要求する代価として、自動追加の
  軽さを一部失ってでも合意に載せる。
- **鍵の権威レコード化(ラウンド 3 F12 — critical)**: §4 の鍵ローテーション「削除」は
  駆動部(check_and_rotate / stage_keys / rotate_keyset)しか消しておらず、P5 違反の
  本体である**カレンダー鍵検証**が無傷で残っていた — EpochManager::current_epoch は
  壁時計導出(certificate.rs:492-497)、is_version_valid は非 current 版を
  registered_epoch + grace_epochs のカレンダーで失効(certificate.rs:322-339)、
  cleanup_stale_keysets が epoch で剪定(certificate.rs:419-428)、proof / 報告検証の
  全経路が epoch 検査を実行(verifier.rs:92-108 / frontier_sig.rs:298-310)。しかも
  「正」とした明示再配布(env + 再起動)は keyset_version を進めない(boot 時に常に
  KeysetVersion(1) — main.rs:760)ため、**再配布 1 回で既発行 proof 全件が署名検証
  不能(偽造と区別不能な invalid)になる** — R2-M2 が名簿層で確立した「検証可能性は
  時間・評価者に不変」の規律の鍵層への未適用だった。裁定:
  1. **公開鍵は名簿レコードに同梱する**: 本節で Raft 一次データに昇格する authority
     名簿レコードに各 authority の Ed25519 公開鍵を含め、**authority の同一性 =
     (id, 鍵)** とする。keyset_version は独立カウンタとしては廃止し**名簿版と同一化**
     する(requirements FR-008 の「keyset_version 単調増加」はこれで初めて実体を持つ —
     §12)。歴史的名簿の無期限保持(R2-M2)がそのまま**歴史的鍵の無期限保持**になり、
     検証手順 2(署名検証)は「pin 版名簿レコードの鍵」で時間・評価者に不変になる。
     roster_hash は鍵も束縛するため、proof への鍵の別建て埋め込みは不要(P9)。
  2. **鍵の有効性は証拠ベースのみ**: 旧鍵版の失効は「新鍵版名簿の Raft commit +
     行き渡り証拠(coverage と同形)」でのみ行う。混在窓は「両版 valid の重なり」として
     扱う。カレンダー失効判定(is_version_valid の非 current 分岐)・
     cleanup_stale_keysets・epoch tick の expiry 用途は**削除対象に追加**する(§4 —
     駆動部削除後はデッドコードだが「将来の呼び出し 1 つで再武装する休眠罠」であり、
     §1 判定基準「転用の発見時即違反」に照らし残置理由がない)。
  3. 明示再配布の runbook には**名簿版 bump 必須 + 両版 valid の重なり規律**を明記する
     (§12)。鍵のみ変更の bump も、id 追加と混在する bump も、統一 ids ⊇ 条件の自動
     forward re-pin(下記 F4/F6 裁定 1 — 収束ラウンド 2 C1/m6)により pending を凍結
     しない(収束ラウンド 1 M5 の「混在は 2 段 bump」規約は削除)。
  4. 受け入れ条件(§9(c))に「鍵再配布をまたいだ既発行 proof の検証成功」と
     「unknown-version(unsupported)と署名不一致(invalid)の区別可能エラー」
     (bls_stub の常時 false と同形の P7 問題の予防)を追加。
  (スコープ縮小案 — 版 bump の強制と歴史 keyset の Raft 保持のみ — でも時間不変性は
  回復するが、名簿と鍵の版が二重化するため P9 上は同梱案が優る、と記録する。)
- **書込時 pin の実体化(ラウンド 2 F1 — critical)**: ラウンド 1 の F5 裁定(pin +
  自己運搬 + 時間不変性テスト)は「評価時点の混入」だけを閉じ、**発行時の分母選択が
  w に束縛されない**穴を残していた — coordinator の pin は揮発性で、再起動時に全 pending
  書込が `resolve_scope` で「現在の」namespace から policy_version を再取得して再構築
  される(certified.rs:402-436, :422)ため、名簿縮小をまたいだ古い書込が縮小後の小さい
  分母で certify される。applied_origins は累積単調(kv.rs:175-182)なので、新名簿下の
  新鮮な報告は過去の全書込を自動的に「覆う」— 縮小方向の false Certified はこの経路で
  現実に起きる。裁定(false Pending は許容コスト、false Certified は死 — P2/P3):
  1. **ack 時の耐久記録**: coordinator は書込 ack 時に `(o, t, key, policy_version)` を
     「当該書込を tracked にする唯一の耐久記録」と**同一レコード**で記録する(現行構造
     では certified WAL。A4 値プレーン統合(§3.6)後は共有 WAL の tracked 書込レコード —
     記録点は構造とともに移るが規律は不変)。restart の pending 再構築・評価時の分母
     導出は**記録済み版を使う** — `resolve_scope` による現在版への再解決は**恒久禁止**。
  2. **proof への自己運搬**: proof は pin 版を「この版は w の ack 時版である」という
     writer の主張として運び、検証は**その版の Raft コミット済み名簿の過半数**に限定する。
     forward re-pin(下記 F4/F6 裁定 1)導入後は、proof は**原 pin(ack 時版)と現 pin の
     2 版(と両名簿)を恒久併載**し、検証手順 5 は二重定足数で両版を検査する(収束
     ラウンド 2 C1 — 原 pin の併載が本項の「ack 時版である主張」を re-pin 後も字義通りに
     保つ)。
  3. **歴史的名簿の保持規律**: 「admission ウィンドウ内」の限定は**撤回**する
     (ラウンド 2 M2: 窓を過ぎた証明書の手順 6 が実行不能になり、時間窓が検証可能性を
     減衰させる P5 違反だった)。保持は**無期限**(版数分すべてを Raft ログ/スナップ
     ショットの一次データとして) — 名簿は小さく(数 KB/版)まれにしか変わらない(§6)
     ので、窓による剪定は問題が実測されるまで設計しない(P9 の先送り規律)。加えて
     「未 certify の tracked write が参照する版は保持必須」を安全側の下限として明記する。
     admission ウィンドウは**新規報告の受理**にのみ適用する。
  4. **名簿縮小時の挙動**: 旧版 pin の書込は新名簿の過半数では certify されない(明示
     re-pin なしに)。書込時名簿の過半数が decommission された場合の**恒久 Pending は
     仕様**であり、F8「decommission = 損失許容の宣告」と整合する。(初版の括弧書き
     「V1 過半数 3-of-5 は残存 3 台の適用で充足可能なので deadlock は必然ではない」は
     **訂正する** — ラウンド 3 F4/F6: 検証手順 1/6 の下で残存台の bump 後の新報告は
     新 roster_hash でしか発行されず旧 pin の証明には使えない。充足可能なのは、bump 前に
     発行済みの旧 roster_hash 報告が下記「プール保持の pin 版対称化」で保持されている
     場合のみ。)救済が必要な場合は**明示 re-pin 運用 API(監査ログ付き)**として提供
     する — 無音の再解決は恒久禁止。
  5. §9 受け入れ条件 (c) に**発行側テスト**を追加: 名簿縮小後、旧版 pin の書込が
     新名簿の過半数で certify されないこと(明示 re-pin なしに)。
  (代替案 B「Raft コミット済みの任意の版の名簿の過半数(証明書内で一貫)へ弱める」は
  検討の上**棄却**: §3.1 の述語文言と「縮小方向 false Certified 構造的に不可能」主張の
  撤回 + durability 弱化の NFR 計上 + 対外主張「過半数が受信・適用済み」の過半数の
  定義変更を伴い、説明コストが案 A より高い。)
- **名簿内容変更と in-flight tracked 書込(ラウンド 3 F4/F6 — critical)**: 書込時 pin +
  検証手順 1/6(証明書名簿ハッシュ = 各報告の署名済み roster_hash = pin 版名簿)の下では、
  authority は常に**現行**名簿の roster_hash でしか署名報告しないため、名簿内容が変わる
  あらゆる版 bump — 縮小だけでなく、本設計が保守方向と位置づける **authority 追加
  (自動再計算を含む)** — の後に発行される報告は、旧版 pin の書込の証明に永久に
  使えない。同時にプール保持(最新 1 件置換)は bump 後最初の報告到着(cadence 1 周期
  以内)で旧 roster_hash の報告 — 旧 pin 書込の証明を組む唯一の材料 — を破棄していた。
  分断常態では coverage 到達まで数日待つ書込が定常的に存在する(§3.4)ため、名簿変更と
  pending 窓の交差は例外でなく**定常事象**であり、放置は「通常のノード追加運用が
  pending バックログ全体を凍結する」ことを意味する。§3.3-4 が仕様として計上していたのは
  縮小方向のみで、拡大方向の未計上は §5「追加は保守方向」の看板と実質衝突し、運用者を
  「名簿を触らない」方向へ誤誘導する隠れコストだった。裁定:
  1. **自動 forward re-pin — 前進条件は id 集合の包含に統一し、証明の定足数は手順 5 の
     二重定足数が別途負う(収束ラウンド 2 C1/m6 で再訂正)**: write w の**現 pin** を
     版 v へ自動前進させてよいのは
     **ids(roster(scope-of-w, v)) ⊇ ids(roster(scope-of-w, pin(w)))**(共通 id の鍵差は
     不問。判定は裁定 4 どおり per-scope の名簿内容ベース)が成立する場合のみ。
     tracked 耐久レコードは**原 pin(ack 時版 — 不変)と現 pin(前進可能)の 2 版**を
     持ち、forward re-pin が更新するのは現 pin のみ — **原 pin の上書きは恒久禁止**
     (収束ラウンド 1 C1 の「同一レコード規律で更新」は原 pin まで前進させる読みを
     許していた — 訂正)。ラウンド 3 初版の bump 隣接 2 版比較が連鎖
     (v1={A,B,C} → v2={A,B} → v3={A,B,D})で false Certified を許した訂正経緯は
     収束ラウンド 1 C1 のとおり。
     **撤回(収束ラウンド 2 C1 — critical 2 件統合)**: 収束ラウンド 1 C1 の健全性論証
     「分母拡大は過半数要求が厳格化する = over-covering」は**算術的に偽**であり撤回
     する。roster(scope, v) ⊇ roster(scope, pin(w)) は「v の過半数 ⇒ pin(w) の過半数」を
     一般に含意しない — maj(|v|) − |v∖pin(w)| ≥ maj(|pin(w)|) が成立するのは奇数サイズ
     pin への 1 台追加のみで、反例は 3 形: 単一の 2 台純追加(pin={A,B,C}、
     v={A,B,C,D,E} — {A,D,E} は v の過半数(3-of-5)だが ∩pin = {A} は 1 < 2)、偶数
     名簿への 1 台追加(pin={A,B,C,D}、v=+E — {A,B,E} の ∩pin = 2 < 3)、1 台ずつの
     純追加 bump の連鎖(re-pin のたびに比較対象の pin が前進するため希釈が累積)。
     いずれも収束ラウンド 1 C1 自身が false Certified の判定基準とした「certify が
     ack 時版の過半数を含意すること」への違反である — 「厳格化」は署名数の下限増加と
     「pin 元定足数の含意」の混同で、過半数要求は絶対数では厳格化するが、集合としては
     pin 元メンバーを 1 人も含まずに充足できる(P2/P3)。
     **新しい健全性構造(re-pin の目的と証明の定足数の分離)**: forward re-pin の目的は
     「報告の roster_hash 整合(authority は現行名簿の roster_hash でしか署名報告
     しない)」の回復であって、証明の定足数の付け替えではない。安全性は証明書組立・
     検証手順 5 の**二重定足数**(下記 — 覆う集合が現 pin 版の過半数、**かつ**原 pin 版
     名簿との id 交差が原 pin 版の過半数)が原 pin 版について直接負い、re-pin 条件から
     独立に成立する。ids ⊇ 条件が保証するのは手順 5 (b) の**活性**である — 原 pin 版の
     全 id が v に残存するため、やがて roster_hash(v) で再報告し両条件に同時に数え
     られる(対価は certify 遅延のみ = false-Pending 方向、§3.4 に計上)。副次効果
     (後続版が旧メンバー id を再包含した場合の凍結書込の自動解凍)もこの構造の下で
     健全 — 解凍後の certify も手順 5 (b) が原 pin 版過半数を要求する。検証手順 0-6 の
     構造は不変で、wasm/SDK の独立検証を弱めない。**これは R2-F1 が禁じた「現在版への
     再解決」の再開ではない**: 禁止の対象は分母が縮小し得る無条件の再解決であり、
     原 pin は不変のまま証明の定足数に残り続ける。**ids ⊇ 不成立(id の縮小・置換)の
     変更への自動 re-pin は恒久禁止のまま**である(裁定 3)。
     **旧 2 類型 + 混在凍結の統一(収束ラウンド 2 m6 — 減算)**: 収束ラウンド 1 の
     第 1 類型(純追加 ⊇)・第 2 類型(同一 id 集合・鍵のみ変更 — M5)・混在 bump
     凍結の 3 分岐は、上記 ids ⊇ の単一条件に統合する。任意の混在 bump(追加 + 鍵変更の
     1 コミット — 危殆化 authority の鍵更新と補充追加の同時実施は現実的な緊急操作)は
     「鍵のみ変更 → 純追加」に因数分解でき、鍵のみ変更成分の健全性は M5 の論証を統合後

**proof ワイヤオブジェクト(FR-008 の API 面 — 先送りしない)**:

proof は内部構造ではなく製品の旗艦成果物(FR-008「検証可能メタデータ」)であり、
`/api/certified/verify` の公開契約(api-reference.md:637-718)が全面的に変わるため、
形とコストを v2 スコープで確定する:

- 形: `{ format_version, reports: [report…], signatures: [sig…], roster: [authority_id…]
  /* = 原 pin 版名簿 */, policy_version /* = 原 pin(ack 時版 — §3.3 書込時 pin)*/,
  pinned_version, pinned_roster /* = 現 pin 版とその名簿(forward re-pin 後。原 pin と
  同一なら省略 — serde(default)。手順 5 二重定足数の材料 — 収束ラウンド 2 C1)*/ }`。
  reports は現 pin 版名簿の過半数分(かつ原 pin 版名簿の過半数を id 交差で覆う分)の
  全量スナップショット報告。`format_version` は append-only 原則の proof への適用
  (ラウンド 2 M8 — SDK/クライアント互換の土台)。
- **署名形式は n 本の Ed25519 報告署名に確定する(ラウンド 2 F10 — 初版の
  「aggregate_sig | [sig…]」両論併記を [sig…] 側で解消)**。理由: checkpoint グリッドの
  削除は、BLS が系内に存在する唯一の理由(全 authority が同一バイト列に署名 →
  fast_aggregate_verify — frontier_sig.rs:10-21)を同時に削除している。現行の報告署名は
  Ed25519 であり、「異メッセージ AggregateVerify への切替」は既存資産の流用ではなく
  **報告内容を覆う新しい BLS 署名レーンの新設**(署名メッセージ構築・DST 選定・keyset
  配線)だった。得るものは proof 6KB 中の 100〜200B(<4%)、失うものは n+1 ペアリング +
  n hash-to-curve の検証コストと P9。さらに wasm ビルドでは blst 自体がコンパイルされず
  (Cargo.toml:16, :35-37)、stub は「Verification always fails」(bls_stub.rs:5)—
  BLS 一本化は旗艦主張「証明書を独立検証できる」を最重要クライアント環境で**構造的に
  不能**にする(§10-5 が「実測コスト」として登録していたのは問題の種別の誤り —
  実測以前に存在しない)。Ed25519 報告署名は全ビルドで検証可能(wasm feature が明示
  サポート — Cargo.toml:35)で ed25519-dalek のバッチ検証も使える。
  「報告署名はすでに報告の全内容を覆っている」(§3.3 冒頭)の論理的帰結そのもの(P9)。
- **BLS は proof 経路から外し §7 cut list に登録**(再着火条件は §7 の行を正とする)。
  裁定記録として残す 2 点: (a) 現行の非 native ビルドは Ed25519 レーンで検証しており、
  BLS 一本化は wasm の検証能力の「欠如」ではなく**退行**だった。(b) bls_stub の常時
  false は「unsupported」と「invalid(偽造)」を区別不能にする P7 問題であり、BLS
  再着火時の受け入れ条件に「非 native ビルドで両者を区別可能なエラー」を含める。
- サイズ試算(authority 5、累積 origin 50、キー名平均 32B、failed_keys 0 の定常時):
  報告 1 件 ≈ origins 50 × (node_id 16B + HLC 16B) + digest 64B + メタ ≈ **約 1.8 KB**。
  proof = 報告 3 件 + Ed25519 署名 3 × 64B + 名簿 ≈ **約 6 KB**(BLS 集約との差は全体の
  1〜2% で試算の結論は不変)。origins 500(引退不履行の累積時)で proof ≈ 50 KB。
  サイズの実質上限は「roster + 未引退 origin 数」であり、**引退規律(§3.2)は平時に
  のみ機能する上限**である(ラウンド 3 F10/m4 — 引退条件 (ii) は authority 1 台の
  長期不在で成立せず分断中は全 origin について停止する。非 roster writer の origin の
  回収は origin-retire 明示操作のみ。分断中の報告・proof 成長は §5.1 の sizing 指針の
  入力に含める)。
- `/api/certified/verify` の v2 契約(上記 proof を受け、検証手順 0-5 を実行し(0 の
  アンカーは帯外鍵レジストリ)、6 はノード上でのみ)は api-reference の実装時更新対象と
  して §12 に登録(SDK 互換計画も §12 — ラウンド 2 M8。実装の段帰属は 5b — §9、
  収束ラウンド 2 m7)。

### 3.4 遅延特性の正直な変化と、証拠を運ぶ車両

現行: certify までの時間 ≈ 報告間隔(データが届いていなくても)。
v2 の正直な記述(初版の「writer → authority の完全転送 + 次の報告」は 2 点で不正確
だった — 多ホップと sync サイクル長の項が抜けていた):

> **certify までの時間 ≈ (直接 pull 接触、または claim キャリア周期 K × sync_interval)
> × ホップ数 + sync サイクル長(現行実装は全 peer 直列 await のため Σ peer RTT —
> node_runner.rs:2436-2439)+ 耐久クランプ項(sync ポリシー別: always ≈ 0 /
> interval ≤ sync 間隔 / off は構成検証で拒否 — §3.2 規律 2)
> + 全量スナップショット報告の周期 + **max(報告配送 cadence, base 全量スナップショット
> 配送完了時間)**(§3.2 配送規律 — resumable 配送は完了時間が cadence を超える環境を
> こそ前提とする(m2 の規律の存在理由)ため、cadence のみの計上は m1 と同型の過小
> だった — 収束ラウンド 2 m3)
> + sweep 項 = **ホップ数 × max(sweep 周期, 1 sweep 完了時間)**(claim 採用は sweep
> 完了に律速 — バックログ / 実効帯域、再開込み。sweep が claim キャリアの正系である
> 以上、バックログ下の多ホップでは claim は 1 sweep 完了波ごとに 1 ホップしか進まない —
> 各中継の applied_origins 前進自体が上流からの sweep 完了に律速される。冒頭の
> キャリア周期 × ホップ数項は digest pull(最適化)が効く定常時の項であり、バック
> ログ下の上界は本項 — 収束ラウンド 1 m1。§3.8)+ gap 治癒待ち(gap 保持中 origin の
> claim 伝播は complete 転送治癒まで停止 — §3.2 規律 4)+ 前進可能 bump(ids ⊇ —
> §3.3)時の forward re-pin 再集積(実効上界 = 旧 base 配送セッションの残余(開始済み
> セッションは完遂 — §3.2 m2 規律により中断不可)+ 新 roster_hash base の配送完了時間
> (バックログ / 実効帯域)。証明書には差分報告が使えない(§3.2)ため delta chain では
> 回復できない — 収束ラウンド 2 m3)**

- applied_origins はクレーム付きの完全 pull(§3.8 sweep)でのみ前進する。認証進捗は
  anti-entropy に律速される。これは「正直さの対価」であり、隠さず docs の遅延特性
  (NFR-002)に載せる(§12)。**「push はクレーム不能」の根拠の訂正と配置制約
  (ラウンド 3 F8)**: 初版の「C-2 の教訓による意図的設計」は誤引用だった — C-2 と
  コードが実際に禁じるのは「pull 成功の push 証拠への流用」(node_runner.rs:3443-3452)
  と「完全性注釈なき部分 push からの claim」(eventual.rs:612-617 — push が LOCAL のみ
  なのは partial だから)であり、完全性注釈つき push(§3.8 sweep の対称形)はどちらにも
  該当しない。それでも v2 が claim 前進を pull 起点に限定するのは **P9(ワイヤ拡張の
  最小化)による裁定**であって、証拠の出所規律の要請ではない — 規律の文言でなく実質を
  引用し続けるため、ここに訂正を残す。帰結として**配置制約を明記する**(NFR-002 /
  ops-guide — §12): certified 進捗と GC authority ゲート進捗は、**全名簿 authority が
  outbound の周期 pull(sweep)を実行できること**を要求する。受信専用 authority
  (outbound 接続を張れない受信局 — 非対称衛星リンクで現実の類型)は非サポートであり、
  GC ゲートは全量要求のため受信専用 authority 1 台で floor 前進が恒久停止する。
  push 方向の対称 sweep(sweep 完了 + 送信側スナップショット S の claim-bearing push)は
  健全に構成可能なので、実需(受信専用 authority の配備要求)を再検討条件として
  §10-12 に登録する(`principles.md` T10)。
- **周期的 claim キャリア(多ホップ問題の解 — 新機構ゼロ)**: 現行 sync 構造の健全経路
  では、増分 delta pull の adoption は sender 自身の origin のみ(node_runner.rs:3911-3922
  — third-origin の全 map 採用は complete pull 限定)で、delta 成功時は digest/full sync が
  恒久スキップされる(:3006 の `continue`)ため、**多ホップ経由でしか authority に
  届かない origin の書込は applied_origins が永久に前進せず、certified が構造的に永久
  Pending になる**。:3908-3910 のコメントが前提する「periodic complete / full sync」は
  未実装(スケジューラ不在)。v2 はこれを設計として実体化する:
  **delta pull 成功時も、K サイクルに 1 回は digest pull(try_digest_pull →
  apply_complete_state)を claim キャリアとして必ず実行する**。digest sync は root 一致
  なら転送ゼロで complete-state 相当の全 applied_origins 採用が健全(:4201-4208 が明文
  保証済み)なので、これだけで third-origin coverage の周期的伝播車両ができる。
  **正系と最適化の位置づけ(ラウンド 2 M3 — 分断復帰直後の縮退の正直な計上)**:
  root 一致は書込静止時のみで、claim キャリアが最も必要な長期分断復帰直後は大半の
  bucket が不一致になり digest pull は実質 full dump(単発 30s 制限)に退化して失敗し
  続ける(§3.8 の限界)。よって **claim キャリアの正系は §3.8 の再開可能 sweep
  (キー空間カーソルの complete pull)であり、digest pull(root 一致時の転送ゼロ)と
  bucket digest スキップはその最適化**と位置づけ直す(ラウンド 3 F1 で per-origin
  接頭辞チャンクは放棄 — §3.8)。
  **pull スケジューリングの責務**: certification worker の誘発対象 origin に加え、
  **GC authority ゲートが要求する「mark された remove の remover origin」(§3.5 —
  ラウンド 3 F3 で要求集合を remover に一本化)を含む** pull を誰かが
  周期スケジュールすることは本節の責務である(未規定のまま実装に渡さない)。
  **per-origin ピア広告の載せ先**: 「`applied_origins[o] >= t` を広告する中継ピア」の
  広告チャネルは現行 peer_frontiers(ピアごとスカラー HLC 1 個 —
  node_runner.rs:4180-4196)には存在しない。**GC レーン報告(per-origin ベクトル —
  §3.2)の受信キャッシュ**を広告構造として使う — 新チャネルは作らない(P9)。
  **依存注記(ラウンド 3 F9)**: この選択により広告の鮮度 = GC レーンの配送前進が
  certify の liveness に入る。§3.2 で配送規律を GC レーンへ一般化したことが本裁定の
  前提条件である(規律なしの GC レーンに載せると、pull 誘発先の発見自体が配送不能に
  律速される)。
- **pull 誘発の到達可能性の一般化**: applied_origins は complete 転送で推移的に伝播する
  (中継 R の全 map が writer W の coverage を運ぶ)ため、certification worker の
  pull 誘発先は **writer 直接である必要はなく「`applied_origins[o] >= t` を広告する任意の
  中継ピア」で足りる**。authority → writer の直接到達可能性(非対称衛星リンクで欠ける
  前提)を仮定しない。
- **サイクル長の設計制約**: 直列ループでは 1 サイクル = Σ(peer RTT) がノード数に比例して
  伸び、certify 遅延がノード数比例で劣化する(P8 と定量的に衝突)。実装方向:
  per-peer 並列化、または certification 対象 origin を優先する pull スケジューリング
  (pull 誘発と同一機構で解ける)。いずれもスケジューリングであり原則上自由。
- 復帰後の coverage 再確立の原子単位は §3.8(再開可能性)が有界化する(再開は送受信
  双方のクリーン再起動をまたいで有効 — 耐久喪失リスタートは新 sweep。§3.8 再開の規律、
  収束ラウンド 1 M7/M3。push 側 = 報告配送の同保証は §3.2 配送セッションの送信側
  耐久化 — 収束ラウンド 2 M8)。
- **受け入れ条件**(実装タスク #7): 多ホップ(writer と authority の間に直接リンクが
  無い)トポロジで certified が前進する統合テスト。**静止トポロジでは自明に通るため、
  「持続書込下 + 分断復帰バックログあり」を条件に含める**(ラウンド 2 M3 — root 一致の
  脱出路を使わせない負荷条件で、再開可能 sweep 経路(§3.8)が実際に運ぶことを検証)。

### 3.5 GC ゲートへの波及

GC の authority ゲートは現在「全 Active range の authority の(時計)frontier が
mark を追い越したか」を見ている。v2 では:

- **authority ゲート — 全量維持の明示裁定**: 初版の「過半数 — FR-010 の規定どおり」は
  **撤回する**。FR-010 の過半数は**checkpoint compaction(操作レコード圧縮、
  compaction/engine.rs)の規定**であり、tombstone floor 前進(不可逆破壊)を許可する
  現行 dual gate の authority 側は意図的に全 authority 報告を要求している
  (node_runner.rs:3657-3675 の `defs.iter().all(...)` + 未報告 1 authority で fail。
  モジュール安全基準は「all known replicas have already incorporated the remove」—
  crdt/gc.rs:33-38)。**二つの破壊操作を分離する**: tombstone floor 前進の authority
  ゲートは全量(母集合 = **authority 名簿 ∪ roster**)を維持し、FR-010 過半数は
  checkpoint 圧縮側だけに適用する。node_runner.rs:3466 の「majority-reach GC is an
  open design question」は本節で「全量維持」と裁定し、close する。
  過半数化は「定足数充足」を根拠にするとはいえ、名簿にいるが roster にいないノードを
  どちらのゲートも待たなくなり、Stage 2 hole-jump と組み合わさると生存ノードだけが
  持つ live dot が floor に潰される — G1(破壊は証明の後)と P4 への違反であり、
  §5 の「dead peer は decommission まで待つ」裁定とも食い違っていた。
- **要求 origin 集合 = mark された remove の remover 集合に一本化**(§10 旧未決点 4 と
  統合。**ラウンド 3 F3** — 初版〜ラウンド 2 の「mark スナップショットに実データ(dot)を
  持つ origin」定義は**削除**する: 下記 R2-F3 の要求ベクトル(remover ベース)とは
  別集合であり(remover は dot を持たないことがある — それが F3 の指摘そのもの)、
  二定義の併記は矛盾だった。また dot 保有定義にしか成立しない「floor 前進でデータが
  沈めば自然に要求集合から外れる」という引退 origin の脱出路も削除する — remover
  ベースでは脱出路である floor 前進自体がゲート通過を前提とし循環する)。
  **引退 origin の充足**: 引退 Raft コミットレコードが同梱する合流位置(§3.2 —
  全 authority 合流を検証した時点の当該 origin の**合流検証時位置**、単一スカラー)を
  第 2 の充足材料とし、ゲートは各 authority について「報告の origins エントリ ≥
  remove HLC」**または**「引退レコードの合流検証時位置 ≥ remove HLC」で充足可能と
  する — 時間でなく引退時に確定した証拠でゲートを閉じる(P4/P5 適合)。**引退
  レコードが充足できるのは合流検証時位置以下の remove のみ**であり、それ以降
  (引退 origin の再活動後)の remove は自動再掲載(un-retire — §3.2 収束ラウンド 2
  M2)後の報告エントリで充足する — 引退は接頭辞のマスクであって恒久宣告ではない。
  合流位置が単一スカラーであることにより、引退後に名簿へ追加された新 authority
  (引退 origin のエントリを報告に持ち得ない)も「引退レコード + ブートストラップ
  complete sync 証跡」の組で閉じられる。
  (代替案「引退前提条件 (iii): 当該 origin の全 remove が floor 未満」は、引退を GC
  前進に順序結合させ、他 origin 起因の GC stall が引退を連鎖阻止するため**劣後**と
  記録する。)
- **欠落は fail-closed + 可観測**: 要求集合の origin が報告に欠けている場合、ゲートは
  不成立とし、阻止理由(どの origin がどの authority の報告に無いか)を counter +
  スロットル WARN で観測可能にする(Phase 0 の可観測化と同じ義務 — P7)。
- **要求ベクトルの出所 = mark された remove 操作そのもの(ラウンド 2 F3 — ラウンド 1 の
  「store の timestamps 由来の per-origin HLC max」は**撤回**する)**: 収集対象は remove
  なのに、live データの timestamps を要求ベクトルの出所にすると remove を系統的に
  取りこぼす — (a) timestamps は上書き意味論で、remove の HLC は後続の別 origin の
  書込で消える(kv.rs:1130/:1148 の insert 上書き。台帳 §2.4)。主根拠は
  record_change/record_change_max の上書き経路(Store::delete の timestamps.remove は
  eventual 経路外なので副論点)。(b) tombstone dot の origin は add の書き手であり、
  remover が dot を持たなければ「mark に実データを持つ origin」に入らない。結果、
  「全 authority が remove を取り込んだ」というゲートの主張が、指定された構成材料からは
  証明できない — G1(認可の根拠が偽になり得る構成)違反。改訂:
  **要求ベクトルは「mark された remove 操作の (remover origin, remove HLC)」から作る**。
  ただし現行構造では deferred dot は HLC を運ばず(or_set.rs:42)、change log の remove
  HLC も後続書込で失われるため、既存記録の流用だけでは不十分 — **remove 時に
  (remover, HLC) を tombstone に併記する(deferred の注釈化)最小の新規記録**を要件と
  する。P9 との緊張の明示裁定: 不可逆破壊の認可根拠(G1)は「新記録を作らない」
  (P9)に優先する。保持は floor 前進まで(floor で沈めば消える)なので有界であり、
  「floor 前進まで保持する新規のグローバル記録」より tombstone 注釈の方が小さい。
  空間規律は不変: authority ゲート比較は HLC 空間、floor walk は dot 空間 — 両者の
  変換・比較は恒久禁止(P1-10、crdt/gc.rs:92-101)。
- **legacy tombstone((remover, HLC) 注釈なし)の移行裁定(ラウンド 3 F7)**:
  (remover, HLC) 併記は remove 実行時にしか記録できず、アップグレード以前に生成済みの
  tombstone には再構成手段が無い(deferred dot は HLC を運ばず — or_set.rs:42、
  change log の remove HLC は後続書込で上書き消失 — 本節 R2-F3 の接地そのもの)。
  floor は連続 walk なので、無裁定では当該 (key, node) の未収集 legacy tombstone が
  それ以降の全 dot の floor 前進を恒久ブロックし、**v2 へのアップグレード自体が既存
  データの GC を恒久停止させる**(解けない fail-closed — §3.2 の混在期ブロックは報告
  形式の新旧しか扱っておらず、この証拠形式の移行ギャップは未規定だった)。裁定:
  - (a) **注釈なし tombstone に限り**、per-origin 要求ベクトルの代替として §3.2 混在期で
    採用済みの**転送証拠 fallback** を適用する — ただし証拠の役割分担を明文で分離する
    (収束ラウンド 1 M1: ラウンド 3 初版の「push 証跡 + complete pull 証跡が安全基準を
    直接証明する」は pull を authority ゲートの証拠列に数える読みを許す、R2-F6 前例
    (push 証跡のみを代替と認めた)からの無論証ドリフトだった。inbound pull 証跡が
    証明するのは「collector が M の状態を取り込んだ」ことのみで「M が remove を
    取り込んだ」ことではない — 「pull は push の証拠にならない」(principles.md P2 系)
    の文言そのもの。コード自身も同じ反例を明文化している: node_runner.rs:3448-3452
    「a pull proves nothing about what the peer received」):
    - **authority ゲートの代替証拠は、R2-F6 と同一の mark 以降の zero-error 完遂 push
      証跡(直接 push 相手)に限定する**。これのみが安全基準「all known replicas have
      already incorporated the remove」(crdt/gc.rs:33-38)を当該メンバーについて直接
      証明する。pull 到達のみ・多ホップ・addr 不明メンバーは §5.1 の dead-peer 裁定と
      同型の stall として受容する。
    - **complete pull 証跡(inbound、母集合 = 名簿 ∪ roster)は hole-jump inbound
      ゲート(crdt/gc.rs:73-90 の「mark 時点で既に hole だった dot」限定論証)の充足
      専用**であり、authority ゲート代替には数えない。pull を authority ゲートの証拠に
      数えたい場合は「M の pulled complete state に当該 tombstone(または被覆 floor)が
      含まれることの**内容検査**」という新機構として、G1/P2 対 P9 の明示裁定つきで
      別途裁定する(gc_inbound_gate_passed のタイムスタンプ痕跡流用
      (node_runner.rs:3585-3599)は内容検証を持たず不可)。
    stall 時の P7 義務(阻止中 legacy tombstone 数と塞いでいるメンバーの列挙を
    gc_gate_diagnose に追加)は不変。
  - (b) §12 ops-guide のローリング手順に「**アップグレード後最初の complete サイクル
    完了 = legacy tombstone の一括収集条件**」を追加する(報告形式の GC 再開条件とは
    別項として)。
  - (c) 棄却記録: アップグレード時の注釈合成((self, now-HLC) を書き込む案)は、合成
    注釈が **remove の伝播を何も証明しない**ため採らない(証拠の出所規律 — 存在しな
    かった証拠を移行時に鋳造することになる)。
  - (d) **注釈の混在期保全(収束ラウンド 2 m2)**: (i) 同一 tombstone dot の注釈付き/
    注釈なしコピーの merge は**注釈を単調保持**する(注釈あり > なし。同一 remove
    なので相違は原理上ないが defensive に max — テストでピンする)。注釈は
    serde(default) の追加フィールドであり、旧版ノードを 1 ホップ経由した伝播では
    剥落する(混在互換の実体である JSON fallback — §3.2 — は未知フィールドを黙って
    落とす)ため、上書き実装は剥落コピーとの merge で保持済み注釈を消し、強いゲート
    材料から push 証跡 fallback への無音降格を許す(P7/G1 — 注釈は remove 実行時に
    しか記録できず剥落は恒久)。(ii) **legacy 母集合は混在期を通じて開いている** —
    旧版ノードでの remove 実行と旧版中継の剥落が新規 legacy を鋳造し続け、分断常態の
    フリートでは全ノード更新完了は無際限(§3.2 混在期の自認)。(b) の「一括収集
    条件」は「**その時点までの legacy 分**の収集条件」と読み、以後の剥落分は
    fallback の定常運用として ops-guide の列挙診断に含める(§12 — P9 の完全形
    「再利用は但し書きごと」: append-only 互換機構の但し書き = 旧読者はフィールドを
    落とす、の輸入)。
- **failed_keys 検査の追加(F1「但し書きごと」規律の §3.5 への適用 — ラウンド 2 F3)**:
  applied_origins の不変条件は merge_failed_keys を除外する(kv.rs:175-191)ため、
  remove の merge が poison で落ちた authority も origins だけならゲートを通過してしまう。
  改訂: **mark キーと authority の failed_keys(報告に同梱済み — §3.2、報告形式の変更は
  不要)が交差する場合、その authority は当該キーの remove を取り込んだ証拠を欠くので
  ゲート不成立**(fail-closed + counter + スロットル WARN — P7)。
  **粒度規定(ラウンド 3 F5 — 実装への明示指示)**: ゲート不成立は**当該キーの mark に
  限定**し、他キーの sweep・floor 前進は続行する。現行 run_gc の単一 bool 構造
  (node_runner.rs:3626-3638)のまま実装すると poison 1 キー(= 恒久ビット)で全 GC が
  恒久停止する — per-mark(per-key)判定への分解を実装要件とし、§9(g) でピンする。
  poison キー自体の tombstone が恒久収集不能になる帰結の計上は §3.2 /
  `principles.md` T9 / §5.1 / §10-10。
- **Stage 2 hole-jump の inbound ゲート母集合も 名簿 ∪ roster(ラウンド 2 F4)**:
  authority ゲートの母集合拡張だけでは、hole-jump が要求する追加の inbound ゲート
  (「mark 以降に全 peer の complete state を merge 済み」— crdt/gc.rs:73-76、実装は
  gc_inbound_gate_passed(node_runner.rs:3589)の registry peers 限定)が盲点のまま残る。
  報告だけ寄越し complete sync を一度もしていない名簿 authority(roster にも registry
  にも入らない)の保有 live dot を collector が取り込んだ証拠は誰も要求せず、hole-jump が
  その dot の hole を潰す — F2 が名指しした破壊が同じ形で残る。裁定:
  **inbound ゲートの母集合も 名簿 ∪ roster とする**(実装対応点は
  gc_inbound_gate_passed の母集合差し替え)。名簿 authority で mark 以降の complete
  pull 証跡を欠く者が居る間は hole-jump 不成立 = fail-closed。報告のみで roster 未登録の
  authority には pull 先 addr すら無い場合があるが、それは**正しく恒久 stall** となり、
  §5.1 の dead-peer 裁定(sync させるか名簿から外すかの運用者判断)と同型に収束する。
  P7 義務: どの authority の inbound 証跡が欠けて stall しているかを counter +
  スロットル WARN で可観測化する(欠落 origin の fail-closed 弾と同じ義務)。
  **claim 蓄積は inbound 証跡の代替にならない(ラウンド 3 F1 — 明示の防波堤)**:
  applied_origins の(sweep claim 由来の)前進がどれだけ蓄積しても、hole-jump の
  inbound ゲートが要求する「mark 以降の complete-state merge 証跡」の代替にはならない。
  inbound 証跡として数えてよいのは mark 以降に**開始**された **sweep の完了
  (= complete pull)記録のみ**であり、部分 sweep は数えない — §3.4 の claim 正系化が
  生む「claim で代用できる」という実装圧力への防波堤としてここに固定する。
  **証跡の時刻基準は sweep の開始時刻(収束ラウンド 1 M2)**: 判定条件は
  `sweep_started_at ≥ mark` であり、**完了時刻基準は禁止** — 数日規模の resumable
  sweep では、mark 前に開始し mark 後に完了した sweep の早期通過キーは mark 前の
  peer 状態しか反映せず、カーソル通過後〜mark の間に peer が獲得した live dot を
  見落としたままゲートが成立し、hole-jump がその dot を破壊する(G1/P4)。開始 ≥ mark
  のときに限り、sweep の per-key 取込保証(各キーで開始時点以降の peer 状態を支配)と
  per-key 単調性(live→存続 or tombstone 化 — いずれも転送される)から「peer が mark
  時点で保持した全 dot の吸収」(crdt/gc.rs:73-76)が従う。これは pull 証跡を開始
  時刻で記録する既存規約(node_runner.rs:4309 `request_start_wall_ms` 挿入、
  :4232-4235「can never overstate freshness」)の踏襲であり、単発転送では開始 ≈ 完了の
  ため無害だった曖昧さを、§3.8 が sweep を任意長化した今、破壊を許す穴になる前に
  閉じる。push 証跡は既に scan 時刻基準(node_runner.rs:3443-3445)で整合。本節
  peer ゲート項の単調時計 / sweep round 番号への置換時も、比較するのは **round の
  開始点**である。受け入れ条件は §9(h)(mark 前開始・mark 後完了の sweep がゲートを
  通らないことのピンテスト)。
  **inbound 証跡のエラー条件 — sweep 局所 zero-error(収束ラウンド 2 M1)**: inbound
  証跡として数えられる sweep 完了(単発 complete pull を含む)は「**当該 sweep 中の
  per-key merge エラーおよび不解読チャンクがゼロ**」の場合のみとする。push 証跡は
  全所で zero-error 完遂を明記する一方、pull 側 = sweep 完了には時刻基準(M2)と
  耐久条件(M3)しか課されておらず、§3.2 規律 4 (ii) が failed_keys 同時採用で部分
  失敗込みの完了を正規動作と定めるため、自然な実装はエラー込み完了を証跡に数える —
  chunk の per-key merge 失敗(型不一致 → poison — kv.rs:183-191)で落ちた寄与の dot は
  collector で hole のまま残り、ゲート成立で floor に潰される = 吸収できなかった peer の
  live dot のクラスタ規模の破壊(G1)だった。**claim 採用(S + failed_keys 同時採用 —
  §3.2 規律 4 (ii))とは条件を明文分離する**: 証跡は hole-jump の complete-merge 前提
  (crdt/gc.rs:73-90)を負い、claim は per-key poison 除外で健全 — 役割が違う。
  **判定は sweep 局所のエラー計数**であり、既存実装の store 全域 merge_failed_keys
  空検査(node_runner.rs:3194-3197, 4304-4307)は**継承しない** — poison は恒久
  (§3.2)なので全域検査の継承は「1 キーでも poison した瞬間、以後の全 sweep が証跡を
  永久に鋳造できず hole-jump が恒久停止する」崖になる(F5/T9 の「poison 1 キーで
  全 GC を止めない」裁定の inbound 側対応 — 既 poison キーへのクリーンな merge は
  吸収を妨げない: データ merge は poison ビットと独立に続行する — G2)。既存の単発
  complete pull 実装の全域検査も同じ矛盾を持つため、実装対応点として同様の局所化
  (当該 pull で新規に落とした寄与のみ検査)を指示する。**防波堤**: 型不一致失敗は
  キー既知なので per-key 除外も理論上可能だが、不解読チャンク(キー未知)を覆えない
  ため sweep 局所 zero-error を採る — hole は dot 空間の欠落でありキーに帰属できない
  (不解読チャンクではキー自体が未知)ため、F5 の per-mark 粒度は inbound 証跡には
  拡張できない。受け入れ条件は §9(h)(エラー込み完了 sweep の否認と、既 poison キー
  存在下の新規エラーゼロ sweep の証跡成立の対テスト)。
- **混在期の GC 停止**: 旧形式報告ノードが残る間の authority ゲート帰結と部分緩和
  (直接 push 証跡の代替)は §3.2 混在期ブロックの裁定を正とする(ラウンド 2 F6)。
- **peer ゲート**(C-2)は既に証拠ベース(完全 push の証跡)であり意味論不変。
  ただし mark と証跡の**時刻表現**を wall-clock ms からローカル単調時計
  (`Instant` 系 / sweep round 番号)に置換し、NTP 補正での後方ジャンプを閉じる
  (台帳 §3.5 最終行)。C-2 の「データ HLC と壁時計を比較しない」規律は
  「データ HLC とローカル単調時刻を比較しない」としてそのまま維持。
- **FR-010「圧縮後も ack_frontier を使って更新反映状況を確認できること」の読み替え**:
  ack_frontier の意味論置換後、この要求は「圧縮後も per-origin 位置(applied_origins
  報告)と compaction floor で更新反映状況を確認できる」と読む(floor は消した事実の
  照会点、報告は到達の照会点)。requirements 側の文言改訂は §12。

### 3.7 やらないこと(このスコープの外)

- **値ハッシュ per-write ack(FastPay 型)**: coverage 証明は「クラッシュ故障の正直な
  authority が値を保持している」ことまでを束縛する。**内容の暗号束縛は report digest
  経由の間接束縛**(digest は store 全体のルート)に留まり、authority が嘘をつく場合の
  防御は従来どおり Byzantine フェーズ。CFT の範囲で意味論を正直にするのが v2 の目標。
- **フロンティア圧縮方式の発明**(BVV 等): 台帳 §2.0 の予言どおり、兼務を解いたら
  証明側に要約は不要になった。GC 側の要約は per-origin ベクトルのままでよい。
  **損失ありの圧縮**は問題が実測されるまで設計しない。ただし**損失なしの転送工学**
  (差分報告・cadence/fanout 分離・origin 引退)はワイヤ形式と署名被覆に影響するため
  先送りせず §3.2 で決定済み — この二つの混同が初版の誤りだった。

### 3.8 coverage 前進の最小単位と再開可能性

初版は coverage 前進の原子単位を規定しておらず、実装上の単位は「バックログ全量を
単発・無中断・30 秒以内の HTTP 転送で受け切る」だった(claims 採用は delta pull 応答
全体の decode 成功時のみ — node_runner.rs:3789-3794 / 採用 :3869 以降。delta 応答は
frontier 以降の全エントリを 1 応答・上限なしで返す — kv.rs:1467-1485。クライアント
timeout 30s 固定 — sync.rs:626)。接触窓が短い/帯域が細い環境では
**backlog > 帯域 × min(30s, 接触窓)** のノードで certify と GC authority ゲートが分断
復帰後に同時恒久停止する — D6 livelock と同根の構造を証明意味論の中核に据えることに
なるため、v2 は原子単位の有界化を coverage 証明の必須要件とする(この要件は本節の
pull 側 = claim 採用に加え、**push 側 = 報告配送にも同様にかかる** — §3.2 配送規律。
ラウンド 2 F9 での一般化)。

**per-origin HLC 接頭辞チャンクの放棄(ラウンド 3 F1/F11 — critical)**: ラウンド 2 まで
の本節は「origin o の HLC ≤ h の自エントリ全部を HLC 昇順チャンクで送り、min(チャンク
末尾 h, 送信側 applied_origins[o]) まで部分 claim を採用する」形だったが、この形は
**健全に実装できない**ため放棄する:

- store は per-key の最終書込 HLC(timestamps — kv.rs:169-171)しか持たず、origin o の
  書込・remove が後続の別 origin の書込で再帰属される(record_change の上書き —
  kv.rs:1129-1131 / record_change_max の前方移動 — kv.rs:1140-1150)と、そのキーは
  o の射影から**無音で脱落**する。チャンクは「per-origin 接頭辞として完全な転送」では
  なく、部分 claim の採用は偽の `applied_origins[o] >= h` を鋳造する(帰結は false
  Certified と、GC authority ゲートの証拠的意味の無効化 — hole-jump 経路と組み合わさる
  と破壊に至る)。min クランプ(旧受け入れテスト)は送信側の値が真に大きい場合を一切
  検査しない。§3.5 の R2-F3 が同じ根本事実(上書き意味論 — kv.rs:1130/:1148)を認めて
  要求ベクトル側を直したのに、claim 側に適用しない内部不整合だった。
- per-key HLC を持たない **untracked keys** は per-origin スキャンに不可視で、complete
  pull が untracked_entries 補償で一度塞いだバグ類型(sync.rs:149-160「receiver would
  claim writes it never received」)を証明意味論の正系に再導入していた。
- 現行 delta が健全なのは「frontier より上の**全 suffix を上限なしで**送り、claim は
  完全転送時のみ」だから(再帰属はキーを常に suffix 内に留める)であり、上限境界付き
  チャンクはまさにその健全性条件を壊す — §7 の教訓「再利用は但し書きごと」のプロセス版
  違反だった。
- 健全化の代替として per-origin 効果索引(書込時 (origin, HLC) → key の順序索引 /
  origin 注釈付き change log)を新設する道もある(ラウンド 3 F11)が、下記のキー空間
  カーソル方式が**新規記録ゼロ**で同じ目的を達するため採らない。将来これを採る場合は
  §3.5 tombstone (remover, HLC) 併記と同族の「G1/P2 が P9 に優先」の明示裁定と保持
  有界化(claim 済み接頭辞の沈降まで)を必須とする、と記録する(番号付き登録は
  §10-14、着火条件は `principles.md` T2 の再検討条件 — 収束ラウンド 1 m5)。
- **last-modified 順走査(delta_entries_since 流用)によるチャンク実装は明示禁止**
  (F11 — 自然な実装経路がそのまま false Certified に落ちる縁であるため、禁止を仕様に
  書く)。

**採用する形: 再開可能キー空間 sweep(= 再開可能な complete pull)**:

- **チャンク境界は HLC でなくキー空間カーソル**に取る。(1) sweep 開始時に送信側は
  自身の applied_origins・merge_failed_keys の**単一原子スナップショット S** を固定
  する(S の applied_origins は §3.2 規律 4 により送信側 gap クランプ済み)。sweep には
  床付き識別子(sweep_id)を与える。(2) 送信側は complete-state 転送と**同一の全 CRDT
  状態(tombstone / 因果文脈込み)**を、決定的キー順の再開可能カーソルで分割転送する。
  timestamps(per-key 最終書込 HLC)を経由しないため、**再帰属・untracked キーの両穴が
  構造的に消える**(F11 の材料不足問題も消滅 — per-origin 順序列挙自体が不要になった)。
- **中間 claim なし**: claim 採用は**全キー空間 sweep の完了時のみ**。採用値は S
  (failed_keys と同時採用 — §3.2 規律 4 (ii)、分離不能規律)。健全性: 送信側状態は
  単調(CRDT merge + applied_origins の単調性)なので、カーソルが各キーを通過した
  時点の値は sweep 開始時点の値を支配し、sweep 完了時の受信側合成状態は**各キーで S を
  支配する**(この論証は**受信側 merge が再起動をまたいで耐久保持されること**を明示の
  前提とする — 下記「再開の規律」の受信側条項。§3.2 規律 4 (iii) と同格の設計不変条件、
  収束ラウンド 1 M3)— 部分 claim を作らなくても**転送の再開可能性**は保たれ、失うのは中間
  進捗の claim 化だけである(certify 遅延は「1 sweep 完了」に律速 — §3.4 の遅延式に
  正直に計上済み)。意味論としては既存 complete pull(apply_complete_state —
  node_runner.rs:4150 系)の adoption と同一で、**原子単位だけを有界化した**ものである
  (P9: 新しい claim 意味論を作らない)。sweep 完了は §3.5 inbound ゲートの
  complete-state merge 証跡になる(部分 sweep はならない。証跡として数える時刻基準は
  sweep の**開始**時刻 — mark 以降に開始された sweep の完了のみ。§3.5、収束ラウンド 1
  M2。**かつ当該 sweep 中の per-key merge エラー・不解読チャンクがゼロの場合のみ —
  判定は sweep 局所で、store 全域の merge_failed_keys 検査は継承しない。claim 採用
  (S + failed_keys)の条件とは分離される — §3.5、収束ラウンド 2 M1**)。
- **再開の規律(収束ラウンド 1 M7/M3 で送信側・受信側の再起動条件を明文化)**: 再開は
  (sweep_id, カーソル位置) の一致時のみ。旧カーソルへの継ぎ足しで claim を作らない
  (fail-closed)。
  - **送信側(M7)**: (sweep_id, S, カーソル) は送信側で**耐久化**し、**クリーン再起動
    (store が WAL で単調保存され、§3.2 の recovery gap 開放が検知されない再起動)**を
    またいで同一 sweep を再開可能とする(S は applied_origins + failed_keys の
    スナップショット — **サイズは報告と同一内容クラスで報告サイズと同階、分断中は
    同じ成長則に従う**。初出の「小さく」は §3.2 の自己計上(試算 115KB〜1MB・分断中
    無際限成長)と矛盾するため撤回 — 収束ラウンド 2 m4。保持コストは §3.2 帯域見積
    (f)。G3 の床規律と同族の永続化)。**回収規律(同 m4)**: 耐久 (sweep_id, S,
    カーソル) は sweep 完了時・無効化時に削除し、保持上限超過時は最古の非活性 sweep
    から破棄する(帰結は当該 sweep の再開始のみ = 安全方向)。耐久化しない場合、coverage
    前進に「送信側連続稼働時間 ≥ sweep 完了時間」という未計上の可用性前提が入り、
    接触窓ごとに電源断・再起動するノード(衛星系の現実の類型)が唯一の supplier の
    とき sweep は毎回無効化され claim は一度も採用されない — §3.8 自身が coverage
    証明の必須要件と宣言した原子単位の有界化(G4/D6)が送信側揮発状態への条件付けで
    破れる。bucket digest スキップも緩和にならない(digest 一致は内容同値であり、
    受信側が送信側に無いデータを持つだけで不一致 = スキップ不能 — 双方向書込下では
    再試行は逓減しない)。**耐久性喪失リスタート(gap 開放検知)では sweep を無効化し
    新 sweep を開始する** — store 退行で S 支配論証が破れるため、耐久化は「クリーン
    再起動に限り再開を許す精密化」であって現行 fail-closed 規則の緩和ではない。
    P7 義務: sweep_id 無効化による再開始 counter。
  - **受信側(M3 — 送信側 fail-closed の対称形)**: 受信側の耐久性喪失リスタート
    (recovery fence 設置と同じ判定条件 — WAL sync interval/off・persistence 無効・
    RECOVER_TRUNCATE)は進行中 sweep を**無効化し新 sweep を開始する**。受信側が
    カーソル(sweep 進行状態)を再起動をまたいで再利用してよいのは、**fsync 済み適用
    位置がカーソル以上であることを保証できる場合**(カーソルを merge と同一 WAL 順序で
    記録し接頭辞一貫で復元する実装 — M-16 耐久クランプと同根)のみ。これがないと、
    fsync 未達のチャンク merge が失われたままカーソルだけ先へ進んだ状態で sweep を
    再開・完了でき、完了時に採用する S が喪失区間の寄与を「適用済み」と主張する —
    R3-F2 が送信側で塞いだ false Certified チャネルの受信側対称形(喪失チャンク区間は
    逐次 merge で再訪されず、§3.2 規律 4 (iii) の gap 治癒(kv.rs:1390-1413)は採用値を
    「完全接頭辞保持の証明」とみなすため汚染はむしろ正規化される。転送の再開可能性は
    必須要件でありカーソル永続化は実装の自然経路 — D5 型の「設計に書かないと実装で
    落ちる」条件)。受け入れ条件は §9(i)。
  - **sweep_id の床(収束ラウンド 1 m6)**: sweep_id の再利用不能性は安全性を負う
    (再開規律は識別子一致のみで再開を許すため、再起動をまたぐ sweep_id 再利用は別
    スナップショットへの継ぎ足し = 不健全 claim 採用の経路)。床は **M-12
    ReportClockFloor と同一機構**(report_clock.rs — §3.2 report_hlc と同じ依拠)に
    依拠する — 新規の床は設計しない(P9。§1 例外台帳 M-12 行の依拠列挙に sweep_id を
    追加済み)。
- **帯域削減は claim 意味論と直交に行う**: 受信側が bucket digest(M-7 系)を添え、
  一致 bucket(= 同一内容の証明)はカーソルがスキップしてよい。スキップは「既に同一
  状態を保持する」証拠による省略であり、S 支配の論証を壊さない。定常時の sweep は
  実質 digest sync + 差分 bucket の再開可能転送に縮退する。
- **pruned_floor の縁**: sweep 完了時の adoption は既存 complete 転送と同じ
  pruned_floor ガード(kv.rs:192-198)に従う(送信側 floor 未満に沈んだ寄与の扱いは
  complete 転送の既存規律を変えない)。
- **既存 delta pull の位置づけ**: frontier 以降の上限なし suffix + 送信側**自身** origin
  の claim(node_runner.rs:3886-3922 の健全性論証)は**そのまま有効**(再帰属はキーを
  suffix 内に留めるため、上限なし suffix + 完全転送時のみ claim という但し書きが守られて
  いる)。delta はバックログが接触窓に収まる場合の最適化であり、収まらない場合の保証
  進捗経路が本 sweep である。push 経路が origin claim を作らないことは不変
  (eventual.rs:613-647。配置制約は §3.4)。
- **ワイヤ**: DeltaSyncRequest への sweep_id / キーカーソルのパラメータ追加。設計方針は
  append-only フィールド + serde(default) + **応答エコー・ガード**(応答が新フィールドを
  エコーしない場合は legacy の complete-delta 意味論として扱い、sweep の継ぎ足し・claim
  採用をしない — fail-closed)。これで A3 Stage 1 復活なしに運べる見込みだが、**運べないと
  判明した場合が §7 A3 再着火条件の発動点**である。roadmap 側は「D6 resumable sync は
  v3 ワイヤ」と既に認識済み(roadmap:68)— 依存関係を §9 に明記。
- **digest 経路の実力と限界(暫定緩和の正直な記載)**: digest pull の root 一致は
  転送ゼロの complete-state 採用(§3.4 の claim キャリア)だが、**root 一致は書込静止時
  のみの脱出路**である。不一致時の bucket 転送は bucket 数 256 固定(digest.rs:64)の
  ため大規模 store では単一 bucket が転送不能サイズになり得る — bucket 粒度の再検討
  (階層化 or 可変数 or sub-bucket 転送)を §10 未決点に登録(本 sweep のカーソルは
  bucket 内部の再開を可能にするため、この限界の実質緩和でもある)。
- **D6(push 側 checkpoint)と対**: pull 側の再開可能性は Phase 0 ではなく
  **coverage 証明(§9 手順 5)の受け入れ条件**に含める(certify の liveness が
  これに依存するため)。
- **NFR-002 への追記指示**(§12): 「分断復帰後の coverage 再確立時間は diff サイズ
  でなく再開単位で有界であること(再開は送受信双方のクリーン再起動をまたいで有効 —
  耐久喪失リスタートは新 sweep。§3.8 再開の規律、収束ラウンド 1 M7/M3。push 側 =
  報告配送の同保証は §3.2 配送セッションの送信側耐久化 — 収束ラウンド 2 M8)」。

## 5. メンバーシップ v2: 明示 roster(v1 A2 の全面差し替え)

### 5.1 設計

GC・certification の安全性が参照する母集合を、**明示的に管理される data-node roster**
に一本化する。

- **roster** = `{node_id → (addr, state, 公開鍵)}`、`state ∈ {active, decommissioned}` の
  **2 状態**(公開鍵フィールドは収束ラウンド 1 M6 — GC レーン報告(§3.2)の受信時署名
  検証の検証鍵の出所。roster 同一性 = (id, 鍵)。鍵は admission の加入意図宣言ハンド
  シェイクで提出し auto-add の Raft commit に同梱、名簿掲載ノードは名簿レコードの鍵が
  優先、roster 鍵の変更は F12-2 と同形の失効規律に従う — §3.2)。
  制御プレーン複製コアの第 4 対象(v1 OwnershipState から epoch / 4 状態
  ライフサイクル / per-scope 化 / vN ラッチ / 証跡刻印を**全部落とした**もの)。
  初版の flat 集合(状態なし)から 1 ビットだけ戻す理由: **削除の痕跡**である。
  flat では decommissioned な node_id と未知の node_id が区別できず、decommission した
  相手の再接触が無音の自動再登録になり、GC 人質のいたちごっこと「人間版 D4」
  (不在中に GC された削除を見ていないノードの無検疫再合流)が仕様上再現する。
  floor が「消した事実」を照会可能に残すのと同型の最小の痕跡(G1)であり、
  decommissioned 集合の成長は**明示操作の回数で有界**(自動では増えない)。
- **追加は保守方向なので自動でよい — ただし接触の定義と admission 条件を持つ**:
  - 「接触」= **認証済み internal API での初回 complete sync 成立時**(単なる ping や
    片方向 push では登録しない)。
  - admission 条件 = クラスタトークンの提示(§6 の token secure-by-default 昇格と結合。
    SSRF/アドレス検証群はアドレス形状しか検証せず、ノードのクラスタ帰属を証明しない —
    誤設定ノード・別クラスタからの誤接続 1 回が恒久 GC 依存を作る事故の一次防壁)。
  - **加入意図の明示(ラウンド 2 M4 — 認証された同期と加入意図を混同しない)**:
    sync ハンドシェイクに**データノード宣言**の明示フィールドを載せ、宣言のない
    complete sync は roster 追加をトリガしない(merge 自体は継続する — P1 非侵食)。
    クラスタトークンを持つ正当な非メンバー用途(バックアップ/ミラー/読取専用
    コンシューマ・意図的短命ノード)が 1 回の sync で恒久 GC 依存(peer ゲートの
    push 待ち相手)になり、1 件ずつの明示 decommission で掃除する恒常負担を防ぐ。
    データノードのデフォルトは宣言 on なので通常運用の自動性は変わらない。
  - **耐久構成の宣言・検証(収束ラウンド 2 M3)**: admission ハンドシェイクで
    WAL sync=always/interval と persistence 有効を宣言・検証する — roster にデータ
    ノード宣言する全ノードは §3.2 規律 2 の構成拒否(sync=off / persistence 無効)の
    対象である(GC 全量ゲートの母集合と報告送り手が 名簿 ∪ roster であるため、
    authority 限定の拒否では非 authority roster ノード 1 台の合法構成が GC の活性の
    崖になる — §3.2)。
  - **既存 roster id と鍵が不一致のハンドシェイク(収束ラウンド 2 m5)**: admission
    としては**拒否**し、アドレス鮮度更新と同様の**自動鍵更新はしない** — 自動更新は
    roster 鍵変更に課した失効規律(新版 roster commit + 行き渡り証拠)の素通しで
    あり、全量 fail-closed ゲートの検証鍵(m1/M6 が証拠汚染防止として必須化)を
    ハンドシェイク 1 回で差し替えられる(G3/P4)。拒否は counter + スロットル WARN で
    可観測化する — 無音拒否は正当な鍵再生成ノード(ディスク交換後の再構築等)の報告を
    恒久検証不能にする D1 型の再発であり、P7 違反(可観測化 + §12 の roster 鍵変更
    runbook への誘導で防ぐ)。鍵の変更は F12-2 同形の明示 Raft 経路のみ(roster 鍵
    変更操作、または decommission → 新鍵で re-admit)。decommissioned 判定自体は
    node_id キーのため鍵に依らず生きる(隔離は破れない)。
  - auto-add の Raft commit には**レート上限**を置く(スケジューリング、適法)。
    junk entry の除去は decommission(1 件ずつの明示操作)なので、追加側の統制が
    運用コストの上限を決める。
- **削除は明示のみ**: `decommission(node_id)` 運用 API。ping 失敗・gossip evict・
  時間経過は roster に**一切影響しない**。
- **decommissioned node_id の再接触**: 自動再登録**しない**。counter + スロットル WARN +
  明示 `re-admit(node_id)` API に落とす。ただし**隔離は membership プレーン
  (roster / ゲート母集合)限定**とし、データ merge / anti-entropy は floor 防御下で
  継続する(P1・G2 との衝突回避 — 収束を止める権利は隔離にもない)。re-admit 時、
  当該 node_id の origin が引退済み(origin-retire — §3.2)なら **un-retire の連鎖を
  必須**とする(引退マスクを残したまま復帰させると、復帰後の新規書込・新規 remove が
  §3.2/§3.5 の再掲載発動まで無音停止する — runbook 明記は §12。収束ラウンド 2 M2)。
- **少数派分断側の auto-add**: roster 変更は Raft 経由なので少数派側では commit
  できない。この間、当該ノードは「未登録 = ゲート外」の既存残余限界
  (node_runner.rs:3465-3467)に落ちることを明記し、ローカルに pending-add を保持して
  過半数回復後にリトライする挙動を仕様とする。
- **authority 名簿との整合**: 現行ポリシーの authority 名簿に載る node_id の
  decommission は**拒否する**(名簿から外すポリシー変更が先)。§3.5 のゲート母集合
  (名簿 ∪ roster)と合わせ、名簿と roster の乖離が破壊ゲートの盲点になる経路を閉じる。
- gossip / ping は到達性(アドレス鮮度・宛先選択・RTT)専用に戻る。
  D4 は「45 秒 vs 10 分」の調整ではなく、**液性が安全性に触れる経路の切断**で根絶。
- 証跡キーの addr → node_id 化(v1 A2 の妥当な部分)は維持。
- decode_response の fail-open 修正(不解読チャンク全キー failed + 続行)は不変。

**dead peer と decommission — 裁定の明文化**:

> **decommission は「死の宣告」ではなく「損失許容の宣告」である。**
> 系自身が「沈黙から死は判定不能」と宣言した以上(§1 判定基準)、オペレータにも死は
> 判定できない。オペレータが判定するのは「このノードが持つかもしれないものを
> 失ってよいか」であり、その判断の期限は時計ではなく**資源圧**が与える。

dead peer は「オペレータが decommission するまで GC が停止する」— これは正しい
fail-closed である。ただし P7(無音は失敗)は「気づける」だけでなく「**判断できる**」
までを要求するため、以下を仕様とする:

0. **暗黙 T の自認(ラウンド 2 — 資源圧裁定の正直な位置づけ)**: 「決断期限は時計で
   なく資源圧が与える」は、grace 窓を消したのではなく **T = 容量 ÷ tombstone 蓄積
   レートという「容量設計が決める有限の決断地平」への置換**である。設計自身の grace
   否定論理(どの T でも T より長い分断は存在する)はこの T にも当たり、それを超える
   分断への答えは「生きているかもしれないノードへの損失宣告」になる — これを隠さず、
   **容量計画 ≥ 最長想定不在 × (tombstone/change-log 蓄積レート + 報告サイズ成長
   レート)** を sizing 指針として(ラウンド 3 m4 — 分断中は origin 引退(§3.2 条件
   (ii))が停止するため、報告・proof も最長不在の間成長し続ける。tombstone のみの
   sizing は過小。**定常メモリ項として GC レーン受信キャッシュ — per-node
   |名簿 ∪ roster| × 報告サイズ、§3.2 帯域見積 (e) — と供給側の耐久 sweep 状態 —
   同時 inbound sweep セッション数 × |S|、§3.2 帯域見積 (f) — も入力に含める
   (収束ラウンド 1 m4 / 収束ラウンド 2 m4)**)
   requirements(NFR-002 遅延特性群)と ops-guide に明記する(§12 — §5.1 が NFR-002 に
   既に適用した「暗黙の読み替えの文書固定」と同じ規律の自己適用)。
1. **判断支援証拠**: peer ごとに、最終 push 証跡・最終 complete pull・**最終の報告到達**
   の記録(提示のみ — 壁時計との比較判定はしない。P5 適法。報告到達は §3.2 配送規律の
   per-peer counter から供給 — ラウンド 2 M6)、**予測復帰の有無**(下記「予定された
   不在」類型の分岐材料)、当該 peer 起因で保留中の tombstone 数と蓄積レート、そして
   「**今 decommission した場合に失われうるもの**」の明文提示(未 push の寄与の有無、
   authority 兼務時の coverage 分母への波及 — 書込時 pin(§3.3)下では pin 版名簿の
   過半数割れ = 当該書込の恒久 Pending、混在期の旧ノードが見ていない remove の伝播、
   **decommission 直後の hole-jump floor 前進が復帰予定ノードの分断期書込を潰すリスク**)。
   あわせて「**旧ソフトノードの正しい救済は decommission ではなくアップグレード**」を
   判断フローに明記する(§3.2 混在期 — 資源圧が健全ノードの損失宣告へ誤誘導する経路を
   塞ぐ)。
2. **資源圧メトリクス**: ゲート不合格で保留中の tombstone 総量 + change-log 増分の
   ゲージ。決断期限を時間定数でなく資源圧(バイトは証拠であり P5 適法)で駆動する —
   「GC 停止がこのレートで続くと容量猶予は X」を系が言語化できること。
   実装は gc_gate_diagnose(range-states.md)への追加フィールドで足りる(P9 — 新機構
   不要)。混在期は「GC ゲートを塞いでいる旧形式ノードの列挙」を含む(§3.2)。
   **poison 起因の恒久阻止分は分離表示する**(ラウンド 3 F5 — poison キーの tombstone は
   decommission でも re-admit でも解けない「決断不能な資源圧」であり、合算表示は
   decommission 判断への誤誘導になる — §3.2 混在期の旧ソフト注記と同族の誤誘導防止)。
   legacy tombstone(§3.5 移行裁定)の阻止分・阻止メンバーの列挙も含む。
3. **runbook**: ops-guide に decommission runbook(判断フロー + 損失確認 + Raft 操作
   手順)を追加し、requirements NFR-002 の「compaction が完全停止しないこと」を
   「**運用操作(decommission)込みで停止しない**」へ明示改訂する(§12 — 暗黙の
   読み替えを文書に固定する)。**runbook の一次分岐に「予定された不在」類型を追加する**
   (ラウンド 2): 衛星コンステレーションでは「数日不在だが軌道力学的に必ず戻る」が
   定常状態であり、損失宣告の意味論は戻ると分かっているノードに対して誤りである。
   この類型は **decommission せず待つ + 当該 peer 向け資源予算の割当・監視**とし、
   decommission は「復帰が予測できない、または予算超過」の分岐にのみ置く。これにより
   「容量 < 最長接触間隔 × レート」構成での decommission→再接触 WARN→re-admit の
   周回反復(各周回が hole-jump の破壊リスクを再演する)を運用の既定線から外す。
   一次分岐にはさらに 2 類型を追加する(ラウンド 3): **「poison 起因」**(資源圧の
   poison 分離分が主因の場合 — **decommission では解けない**。ops-guide の回避策と
   §10-10 の隔離退避へ分岐。F5)、および**「生存しているが名簿掲載のまま長期遅延する
   Authority」**(m7 — 本節冒頭の decommission 拒否により、実手順は「ポリシー変更で
   名簿から外す(Raft)→ roster から decommission(Raft)」の **2 段**であり、名簿縮小は
   旧版 pin 書込の凍結 / 明示 re-pin(§3.3)を連鎖させる — この連鎖込みで判断させる。
   NFR-002 の要件文言も同粒度まで具体化する — §12)。

**待つコストの有界化(第三の方向 — §10 に登録)**: 本裁定は「待つ**時間**の有界化
(禁止)」と「損失宣告」の二択に固定しない。**待つ**コスト**の有界化** — 不在 peer
のみに阻止された保留 tombstone/change-log の cold tier 退避(証拠は消さない。再接触時に
再水和 — G1/P5 適法)・per-peer バックログ予算 — は原則に触れない設計方向であり、
採否は実測後でよいが、検討なしの二択固定は解消しておく(§10)。

Phase 0 の可観測化(ゲート阻止理由の counter/WARN)はこの前提条件であり続ける。

## 6. リーダーと north star の再検討(台帳 §4)

- **合意が本当に必要なのは「roster と policy/authority 定義の変更」だけ**であり、
  これは authority 名簿の split-brain(二重名簿での二重 certify)を防ぐという
  安全性要件から来る。ここに選出リーダー(Raft)を使うのは妥当。ただし:
  - **authority 名簿(自動再計算の結果を含む)は Raft コミット対象の版付き一次データに
    昇格する**(§3.3 — certification の分母を評価時点から切り離すための代価)。
  - 読みは結果整合であることを docs で正確に表現する(「CP」の一語で済ませない)。
  - 「ポリシーを変えたいのは分断の最中」への答えは「分断中に変えられないのが安全」
    ではなく「**分断前に分断時挙動をポリシーとして設定しておく**」
    (allow_local_write_on_partition 等)であることを user-guide の設計思想として明記。
- **north star(Scatter 型 range 委譲)は撤回し、研究オプションに降格する。**
  リーダーを N 個に増やす方向は「この系はリーダーレスが強み」という原則と逆行する
  (台帳 §4.4)。スケールアウトの再定義:
  1. 合意フットプリントを「まれにしか変わらない小さな状態」に閉じ込め続ける
     (roster + policy + authority 名簿版のみ。データ・証明・GC は既にリーダーレス)。
  2. データプレーンの部分複製(配置ポリシーが実際に複製先を絞る配線)。
  3. certification は per-range 名簿 + 報告集めで既にリーダーレスにスケールする。
     ただし報告メタデータの O(origins) 性は `principles.md` 緊張表 T3 に登録済み
     (ラウンド 3 m6 で §1 台帳から移管)であり、
     未踏主張との緊張は §3.2 の転送工学と origin 引退で緩和する。
- `control-plane-scaleout.md` の制約群の改訂: **C1(per-scope epoch キー)は削除**
  (委譲前提の前払いだった)。C2(単一版数への新規依存を増やさない)・C3(voter 静的)・
  C5(準備状態の唯一定義点)・C6(Bootstrap ルート専用)は原則の系として存続。
  C4(交渉層の上)は「新バイト形を作らず append-only で設計せよ。できない場合に
  初めて交渉層を設計する」に緩和(§3.8 の応答エコー・ガードがその適用例、失敗時は
  §7 の再着火)。
- BFT 非対称(voter 1 台侵害で全署名投資が迂回される)は CFT スコープの受容として
  docs に明記済みの方針を維持しつつ、**token secure-by-default**(未設定時の internal
  API 拒否/大警告)を近接パッチ群に昇格する(数行級、followup「再考すべき受容済み限界」。
  §5.1 の admission 条件の前提でもある)。
