# AsteroidDB 原則章程(principles)

作成: 2026-07-30(設計検証ラウンド 1)。位置づけ: **docs/design/ 全文書の上位規範**。
実装コードからの帰納(系統 A)とビジョン文書からの演繹(系統 B)の 2 系統の導出を統合した
確定版であり、以後の設計改訂は本章程との整合を保つこと。原則と衝突するが意図的に残す
ものは `core-semantics-v2.md` §1 の**例外台帳**に登録する(登録なき衝突は欠陥)。
同台帳はラウンド 3 m6 で 2 判定基準(壁時計・沈黙)対応の例外に純化された — 非時間系の
原則間トレードオフは本章程の**緊張表**(T3 / T9 が判例)が登録簿である(v2 §1)。

## 精神性(前文)

この DB が一貫して守るのは「**クライアントと未来の自分に嘘をつかない**」ことである。
分断と沈黙が常態である環境で、嘘をつくくらいなら止まり、止まるなら声を上げ、待つべき
相手は証拠と明示の合意でしか減らさない。絶対に譲らないのは三つ — 分断中でも Eventual
書き込みは受理され続けること(可用性の下限)、certified という語が「過半数が受信・
適用した」ことの検証可能な証明以外を決して意味しないこと(false Certified の構造的
排除)、真偽・安全の判定を壁時計と応答の不在に決して委ねないこと。その対価として、
遅延(412、再起動後の Pending 退行)、帯域(冗長 re-push、O(origins) 報告)、可用性
(dead peer が GC を止める)、自動化(dead peer 除去・鍵再配布は人間の明示操作)を
潔く支払う。系全体を貫くのは「**誤りは必ず保守方向に落ちる**」という単一の向き —
over-covering は安全、under-covering は嘘、false Pending は対価、false Certified は死 —
であり、この向きを frontier からセッショントークン、GC ゲート、ワイヤ互換まで
例外台帳付きで貫徹することが、この製品の差別化の実体である。

## 原則

- **P1: 分断中でも Eventual は書ける(可用性の下限は交渉不可)。** いかなる機構
  (証明・GC・制御プレーン・ポリシー配布・membership 隔離)もこの下限を侵食しない。
  分断時挙動はポリシーで「分断前に」設定しておくのが正解と定義する(v2 §6)。
- **P2: certified は嘘をつかない。** certified と名乗る応答は「区画の権威名簿の過半数が
  当該書き込みを受信・適用済み」を独立検証可能な証明で裏付ける。証明できなければ
  Pending と言う。系: **証拠の出所規律** — 証拠は取得経路が実際に証明する範囲でしか
  主張しない(pull は push の証拠にならない、部分転送から完全性 claim を作らない)。
  系: 証明に使う frontier は、その不変条件の**但し書きごと**運ぶ(poison 集合・
  recovery gap と分離した frontier は証明ではなく捏造 — kv.rs の invariant、v2 §3)。
- **P3: 誤りは常に保守方向に落とす(fail-closed)。** 「持っていないのに持っていると
  言う」変換は圧縮ではなく捏造であり全域で禁止。「持っているのに待たせる」は許容
  コスト。過剰カバーは安全、過少カバーは嘘。
- **P4: 沈黙は情報ではない。** 待つべき相手の集合(GC 母集合・certification 分母・鍵の
  有効性)を応答の不在・時間経過で自動的に狭めない。縮小は明示操作か過半数合意のみ。
  追加(保守方向)のみ自動化してよい。系: **信頼の根は液性ドメインに追従させない**
  (Raft voter 静的、gossip/ping は到達性専用)。
- **P5: 物理時間は真偽を決めない。** 壁時計・TTL・epoch は「いつ仕事をするか」のみ。
  判定基準: その時刻値を変えて安全性が変わるなら違反。系: **順序空間の分離** —
  dot カウンタ・HLC・壁時計は別の順序空間であり、比較・変換して安全判定に使わない
  (HLC からの floor 導出禁止 = P1-10)。
- **P6: 単一クラスタ・単一ポリシー面での統合。** Eventual と Certified は同一クラスタ・
  同一 control-plane・同一の複製/永続化/観測基盤を共有する(値プレーンの統合)。
  ただし意味論の混同はしない(証明状態の揮発性は値の永続性と意図的に分離)。
- **P7: 無音は失敗。** 安全のために止まる・捨てる・拒否する箇所は必ず counter +
  スロットル付き WARN で観測可能にする。P3/P4 は P7 なしでは運用不能(D1 型の無音
  永久停止を量産する)— 片方だけの採用は有害。系: **有界化は機能停止ではなく退避 +
  文書化された弱化で**。ただし安全必須データ(署名報告の origins 等)は退避不可なので
  「安全方向への段階縮退 + 可観測」に倒す(v2 §3.2 — 超過分の欠落は under-covering
  方向のみ。ラウンド 3 F10/m3 で「超過時の報告失敗(拒否)」から置換)。
- **P8: ノード追加でスケールが閉ざされない。** 全体合意は「まれにしか変わらない小さな
  核」(roster + policy/authority 定義)に閉じ込め、データ複製・証明・GC・anti-entropy
  はリーダーも全体同期点も持たない。
- **P9: 減算的設計。** 新しい格子・バイト形・時間窓・状態機械を足す前に、系が既に持つ
  正しい道具(per-origin 格子、append-only + serde(default)、証拠ベースゲート)で表現
  できないかを先に問う。将来要求の先取り機構は実測まで作らない。**消すものの列挙を
  設計の必須成果物とする**。再利用は但し書き・除外節ごと持ってくるのが完全形
  (半分だけの再利用は新しい嘘を作る — v2 §11 F1 の教訓)。

### 補則(実装帰納 — 上記の具体形として全域に適用)

- **G1: 破壊は証明の後、痕跡を残して。** 不可逆操作(tombstone GC、compaction floor
  前進)は全関係者の適用証拠が揃ったときのみ。消した後も「消した事実」を再検査可能な
  形(floor、decommissioned マーカー)で残す。証拠が揃わなければ無期限に止まる
  (P3+P4 の系、P7 が運用可能性の条件)。
- **G2: 収束は例外処理より強い。** リモート寄与の merge は時計エラー・WAL 失敗でも
  止めない。失敗は当該キーの poison として frontier と**分離不能に**記録し、収束は続行。
- **G3: 存在を証拠に使うなら、その存在の生成経路を封じる。** 証跡・floor ファイルの
  存在を証拠とする場合、生成・復元の全経路を統制する(write-ahead lease 床、grace 中
  無署名、バックアップ復元禁止 — M-12)。**識別子の再利用可能性は自己冤罪穴**であり、
  署名済み識別子には床付き単調性を要求する(v2 §3.2 report_hlc)。
- **G4: 送らない・書かない最適化は「無変化の証明」とセットでのみ。**
  `changed == false ⟹ pre == post` の機械的契約が成立するときのみ許し、疑わしい状態
  (poison)では冗長側に倒す。ただし冗長性の許容にも前進性の下限が要る(D6 —
  再送の原子単位は有界でなければならない。pull(claim 採用)と push(報告配送)の
  両側に適用する。v2 §3.8 / §3.2 配送規律)。

## 既知の緊張と裁定方針

| # | 緊張 | 裁定(確定分) |
|---|---|---|
| T1 | fail-closed(P3/P4/G1)vs 進捗・資源(NFR-002 laggard 耐性) | 止まる側に倒す。ただし P7 の可観測化 + 判断支援証拠 + 資源圧メトリクスを必須とし、decommission を「死の宣告」でなく「**損失許容の宣告**」と定義(v2 §5)。requirements NFR-002 は「運用操作込みで停止しない」へ改訂指示(v2 §12) |
| T2 | 正直な証明(P2)vs 遅延(NFR-002) | 正直側。coverage は anti-entropy に律速されることを遅延特性として公表し、原子単位の有界化(再開可能 sweep、claim キャリア周期)で「遅い」を「到達不能」にしない(v2 §3.4/§3.8)。claim は sweep 完了時のみ採用(中間進捗の claim 化は健全性の対価として放棄 — ラウンド 3 F1) |
| T3 | P2 の O(origins) メタデータ vs P8 スケール主張 | P2 優先で受容(**本行が登録簿** — v2 §1 の例外台帳はラウンド 3 m6 で 2 判定基準(壁時計・沈黙)対応の例外に純化し、非時間トレードオフは本表が保持する)。緩和は損失なし転送工学(cadence/fanout 分離・差分報告・origin 引退)を v2 で決定し、損失あり圧縮のみ実測まで先送り(v2 §3.2)。**弱化の文書化(ラウンド 3 F10/m4)**: origins の定義域は roster で有界化されない(歴史上の全 origin の累積 + 非 roster 正当 writer — 回収は origin-retire 明示操作のみ)。引退条件 (ii) は分断中成立しないため転送工学の一角(引退)は平時にのみ効く — 分断中は報告・proof が成長し続け、sizing 指針の入力に入る(v2 §3.2/§5.1)。超過時は段階縮退(roster 現役優先の欠落 = under-covering)。**再検討条件**: 転送工学適用後も報告配送(v2 §3.2 配送規律)が実環境帯域で前進しないことが実測された時 |
| T4 | Certified の分断時失敗(P2 strict)vs P1 | 意図的非対称であり衝突ではない。ただし整合性の強い側が可用性・耐久性で劣る「倒立」(D2/D9)は欠陥であり、P6 の値プレーン統合 + 報告の耐久クランプで矯正(v2 §3.2/§3.6) |
| T5 | P8 の「閉ざさない」前払い制約 vs P9 減算 | 実需が出るまで払わない(C1 削除が判例)。カット判定には反証可能な再着火条件を必須とする(v2 §7) |
| T6 | LWW「後勝ち」の物理時間意味論 vs P5 | プロダクト仕様として例外台帳に明示(v2 §1) |
| T7 | 有界化(P7 系)vs 健全性 | クライアント側ステートレス構造(セッショントークン)の間引きは文書化済み弱化として許容。**サーバ間の安全必須データ(authority 報告 origins)には間引きを輸入しない** — 全量必須 + 超過は安全方向への段階縮退(roster 現役優先・超過分の欠落 = under-covering)+ 可観測(v2 §3.2 — ラウンド 3 F10/m3 で「超過は拒否」から置換。T3 の弱化文書化と同一裁定)。方向が逆の先例を安全性根拠に引用しない(証拠の出所規律の文書版) |
| T8 | 単一 control-plane(P6)の Raft リーダー vs リーダーレス優位(P8) | 合意は roster + policy 核のみに閉じ込めて受容。Scatter 型 range 委譲は研究降格(v2 §6) |
| T9 | poison(merge_failed_keys)の恒久性・伝染性(G2 の正直化)vs 可用性・資源 — 恒久 false-Pending(certify 側)+ **恒久収集不能 tombstone**(GC 側: v2 §3.5 failed_keys ゲートとの合成。decommission にも re-admit にも対応操作が無い「決断不能な資源圧」) | 受容(過少主張なので P3 適合。v2 §1 例外台帳からラウンド 3 m6 で本表へ移管)。counter + WARN + 資源圧の poison 分離表示(v2 §5.1)で可観測化し、ops-guide に回避策(キー作り直し — 旧キー delete のトレードオフ込み)を記載。ゲート不成立は per-mark 粒度に限定(poison 1 キーで全 GC を止めない — v2 §3.5)。証拠ベース un-poison は実需まで作らない(v2 §7/§10-9)、key 単位隔離退避は v2 §10-10。**再検討条件**: (i) 恒久 poison キー数・伝染範囲の実測が回避策の運用コストを超えた時、(ii) poison 起因の収集不能 tombstone 蓄積が資源圧メトリクスで実測された時(ラウンド 3 F5) |
| T10 | claim 前進の pull 起点限定(P9: ワイヤ拡張最小)vs 受信専用 authority トポロジの活性(P1 系 — 非対称衛星リンクは対象環境の現実の類型) | pull 限定を維持し、配置制約(全名簿 authority に outbound 周期 pull 能力を要求 — 受信専用 authority 非サポート、GC は 1 台で恒久停止)を NFR/ops-guide に明記(v2 §3.4)。注釈付き完全 push は証拠の出所規律に反しない(C-2 が禁じるのは pull 成功の流用と注釈なき部分 claim — 誤引用は訂正済み)ため、push 対称 sweep を v2 §10-12 に登録。**再検討条件**: 受信専用 authority の実配備要求が生じた時(ラウンド 3 F8) |

## 運用規則

- 新規の wall-clock 定数・時間窓・母集合変更・証拠経路は、レビューで P5/P4/P2 の判定
  基準(v2 §1)を機械的に適用し、例外は例外台帳の更新とセットでのみ導入する。
  例外台帳の各行は**再検討条件**(その例外が不要になる/許容できなくなる反証可能条件)を
  持ち、棚卸しは例外の追加だけでなく**既存例外の再検討条件の成立チェック**を含める
  (v2 §1 — cut list の再着火条件との対称性。登録は「登録漏れ」を防ぐが「登録による
  無限受容」は防がない、への構造的対処)。
- 本章程の改訂は、衝突する実コード判断(帰納根拠)か vision/requirements の改訂
  (演繹根拠)を伴う場合のみ行う。
