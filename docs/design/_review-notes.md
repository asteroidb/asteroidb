## 0. 通底する原則(問題の判定基準)

> **沈黙は情報ではない。核となるロジックに物理時間を入れてはいけない。**
> 何が真か・何が安全かを決める判断に入ってよいのは、各ノードのローカルな時系列と、
> それらを統合したときに意味づけられる全体の時系列だけである。

物理時間を入れてよいのは「いつ仕事をするか」(報告間隔・スナップショット周期・圧縮トリガ・
保持期間の下限・ログのスロットル)であって、「何が真か」ではない。

分断環境では応答の不在は「死んだ」の証拠にならない。むしろ「生きているのに黙っている」が
常態であり、それがこのシステムが前提とする環境そのもの。

**このコードベースは既に正しい原則を部分的に持っている**(壊すな核の「データ HLC と壁時計を
比較しない」、A3 が TTL を明示却下、A4 の Timeout が終端でない、GC は「いつやるか=時間 /
やっていいか=証拠」を正しく分離)。適用されていない箇所が問題。

## 1. 証明が何も束縛していない ★最深部

### 1.1 フロンティアにデータ依存が無い

フロンティア報告に載る時刻は、**その authority が報告時に自分の論理時計を読んだ値**である。
論理時計は壁時計が進めば無条件に進むため、**データを 1 バイトも受け取らなくても前進する**。

したがって「過半数の authority のフロンティアが書込のタイムスタンプを追い越した」は
「過半数の authority の**時計が経過した**」でしかない。書込がそのノードに届いたかどうかとは
無関係に、報告間隔ぶんの壁時計が経てば成立する。

文書(requirements.md FR-008、architecture.md)は ack frontier を
「各 Authority が取り込んだ更新時刻の到達境界」と説明しており、**完全性を含意している**が、
実装が満たしているのは到達性のみ。

### 1.2 証明書が内容を束縛していない

署名は 2 本ある。**報告署名**は報告の全内容(ダイジェストを含む)を覆う。
**証明書署名**は `(区画, チェックポイント, ポリシー版)` の 3 つだけを覆い、**ダイジェストを含まない**。

証明書を組むのに使われるのは後者。よって**内容束縛は二枚舌検知にだけ効いていて、
証明書の意味には一切効いていない**。

### 1.3 certified 値が複製されていない(D2)

certified 書込は専用のストア・専用の時計・専用の WAL を持ち、既存の delta/digest 同期は
eventual ストアしか見ない。**証明は複製されるが値は複製されない。**
書いたノードを失うと誰も値を読めない。整合性の強い側が可用性で劣るという倒立。

### 1.4 読取の状態判定が値と結びついていない(D3)

状態判定は未確定リストと確定キャッシュを**キー名だけ**で引いており、
**ストアの現在値のタイムスタンプと突き合わせていない**。
certify 後にそのキーが eventual write で上書きされても certified を返し続ける。

また 2-step 運用(FR-004)が実装されていないため、未知のキーは永遠に Pending。

### 1.5 帰結

証明書が実際に主張しているのは:

> **この区画の権威名簿の過半数が、このポリシー版のもとで、このチェックポイントに署名した**

これだけ。以下は一切証明されていない:

- あなたの値が彼らに届いたこと(1.1)
- 彼らのストアがあなたの値を含むこと(1.2)
- 値が複製されていること(1.3)
- 読んだ値が certify された値と同じであること(1.4)

## 2. フロンティアの表現が因果履歴の「圧縮」になっていない

### 2.0 ★ 根本: 1 つの構造が 2 つの仕事を兼ねている

**圧縮が難しいのは、圧縮方式の選択が難しいからではなく、フロンティアが要求の異なる 2 つの
仕事を同時に負っているからである。**

| 仕事 | 要求 | 粒度 |
|---|---|---|
| **証明** — 「あなたの書込を過半数が持っている」を第三者に示す | 暗号的な重み / 内容束縛 / 公開検証可能 | **特定の 1 書込**について答えればよい |
| **GC** — 「全員がこの削除を見終わった」をローカルに判定する | 署名不要 / 集約検証不要 / チェックポイント整列不要 | **全体の到達状況の要約**が要る |

要求が直交しているものを 1 つのスカラーに背負わせた結果、どちらも satisfy できていない
(証明は到達性しか言えず §1、GC は laggard に律速される §3)。

**`../research/whitemap.md` はこれを設計の単一最大衝突点として既に名指ししている**:

> **⚔T2 frontier 集約の min 性が三者を単一パラメータで縛る**: ack_frontier の緩和度・粒度が
> 「Certified 進捗性」「causal GC 安全性」「laggard 耐性」を**同時に**決める。設計の単一最大衝突点。

帰結として、**§2.3 の「情報量の下限による衝突」は一部が構造由来で、真の下限ではない可能性がある**。
兼務を解けば、要約を必要とする仕事が減り、残った側の要求も緩む。逆に兼務したまま圧縮方式だけを
最適化しても、3 つの要求を 1 パラメータで縛る構造は残る。

**この会話で圧縮方式(BVV 形 等)を検討した結果、いずれも「概念を増やす」方向にしか行かなかった
のは、問題の切り分けが誤っていた可能性が高い** — 出発点の過剰設計批判(§8)と同じ方向に
自分が進んでしまう兆候として記録する。

### 2.1 落とす向きが逆

圧縮であれば、落とす方向は保守側でなければならない。
「持っているのに知らないと言う」は可用性の損失で許容できるが、
「持っていないのに持っていると言う」は健全性の破壊。

**現行のスカラーは後者の方向に落ちている。** したがってこれは因果履歴の圧縮ではなく、
因果履歴とは無関係な別の量への置き換えになっている。

### 2.2 この系で唯一ベクトルになっていない格子

同じシステムの中に、発信元ごとのカウンタで表現された格子が既に 3 つある:

- **OR-Set のドットカウンタ**(発信元ごとの単調カウンタ = バージョンベクトル)
- **compaction floor**(発信元ごとの連続接頭辞、pointwise max で join)
- **セッショントークン**(発信元ごとの位置の集合。`is_satisfied` は本物の完全性判定)

**フロンティアだけがスカラーの壁時計。** しかも弱い保証(セッション)の方が正しい道具を
使っているという逆転が起きている。

### 2.3 圧縮設計の衝突(ただし一部は §2.0 由来)

要約に求めたいのは 4 つ — 健全性 / 簡潔性 / 合流性 / 判定容易性。
バージョンベクトルは簡潔性を欠き、スカラーは健全性を欠く。
因果履歴は本質的に発信元ごとの情報を持つので、1 個の数に潰すと必ず何かが落ちる。

**ただしこの衝突がどこまで真の情報量の下限で、どこからが §2.0 の兼務由来かは切り分けられていない。**
「特定の 1 書込について答える」だけなら要約は不要であり、4 要求のうち簡潔性の圧力は
**要約を必要とする仕事にしかかからない**。下限として扱う前に、兼務を解いたときに何が残るかを
確定させる必要がある。

### 2.4 実装上の障害

- **HLC が疎であること自体が、既存の圧縮技法を無効化している。** DVV/DVVS の
  「`(r, m, n)` で m+1 から n-1 が穴」というコンパクト区間表現は識別子が**密な連続整数**である
  ことに依存するが、HLC は Unix ミリ秒 + 論理カウンタで連続にならない
  (`../research/topics/logical-time.md` が「適用不可、ビットマップ方式か変換層が必要」と名指し)。
  これは compaction floor の「HLC から床を導出することは永久禁止」(dot カウンタ 10⁰〜10⁶ vs
  HLC 物理 10¹²)という既知の教訓と**同じ空間混同**の別の現れ方である。
- ストアのキーごと HLC は**上書き意味論**でキーごと単調でない(A4 設計文書が明記)。
  「このキーの最新書込の発信元と位置」をストアから素直に取れない。
- 発信元集合が変わったときの比較の意味が未定義。定義域自体に合意が要る。
- 書いてから離脱した発信元のエントリは、その書込が floor 以下に沈むまで捨てられない
  → **死んだピアが GC を人質に取る問題(§3.1)と同じ形**に合流する。

## 3. 時間から安全性・合意を導出している箇所

### 3.1 メンバーシップ(D4)

gossip は ping 3 連続失敗(≒30〜45 秒)で peer を registry から完全消去する。
GC の安全性母集合が同じ registry を見ているため、**45 秒を超える分断で生きているピアが
「待つべき相手」から消え、GC がその先へ進み、復帰時に生きているデータが破壊される**。

高遅延・分断環境向けを掲げるシステムで 45 秒が致命傷になる。

### 3.2 grace 窓による緩和も同じ推論のまま(設計案)

A2 Phase 1 の grace 窓(既定 2×gc_retention = 600 秒)は、**同じ推論を 10 分に延ばしただけ**。
`membership-epochs.md` §5 が自認:

> 分断が grace 窓を超えると現行と同じ挙動(母集合から消え証跡も刈られる)

同 §6 の「e2e で grace 既定の妥当性を実測確認」も問題。
**分断の長さを決めるのはネットワークであってチューニングではない。**
どの値を選んでも「それより長い分断」は定義上存在する。

### 3.3 チェックポイントの 1 秒丸め

全 authority が同一バイト列に署名する必要から、フロンティア時刻を 1 秒グリッドに切り下げている。
**合意を時間の量子化で買っている。**

正しい値が「誰も気づかないくらい小さい値」であるようなパラメータは、
そもそも存在すべきでないパラメータ。1 分にすると醜さが見えるということは、
1 秒でも同じ醜さが見えていないだけで存在しているということ。

### 3.4 鍵の有効期限 ★分断環境で実際に壊れる

鍵セットは 24 時間 epoch × 過去 7 epoch 猶予。
つまり **8 日を超えて接触を失ったノードは、復帰時に全員から鍵を拒否される。**
衛星コンステレーションを掲げるシステムで 8 日の不接触は異常事態ではない。
しかも復帰ノードは自分の鍵が古いことをローカルに判断できない。

鍵の失効は本来「新しい鍵が全員に行き渡ったことを確認したら旧鍵を無効にする」という
証拠ベースの操作であるべきものが、カレンダーで決められている。

さらに**自動ローテーション自体が未配線**(切替を起動する production 経路が無く、
ローテーション判定は常に no-op)。**「使われていない危険な機構」**という最も良くない状態。

### 3.5 その他の時間依存

| 箇所 | 問題 |
|---|---|
| 証明の Timeout | 壁時計経過が**状態遷移**になっている(表示であるべきものが状態を変える) |
| fence 後の猶予期間 | フロンティア記録の掃除が時間ベース(「全 authority が新版で報告した」で表現可能なはず) |
| 二枚舌の保持窓(120 秒) | 検知範囲が壁時計。観測数か因果位置で表現可能なはず |
| digest 非対応キャッシュ TTL(10 分) | **A3 の新設計は TTL を明示却下しているのに既存が TTL のまま**(自己不整合) |
| GC ゲートのローカル時刻 | 形は正しい(ローカル対ローカル)が壁時計なので **NTP 補正で後ろに飛ぶ** |

### 3.6 外部アンカー依存(単純には消せない 2 つ)

**HLC のスキュー拒否(60 秒)** と **attestation の遠未来拒否(60 秒)** は、
「壁時計という単一ノードには偽造しにくい外部参照」に依存している。
純粋に論理的な系では「遠すぎる未来」という概念自体が存在しないため、この防御は書けない。

ただし観察: **スキュー拒否は HLC の物理成分が自分で開けた穴を塞いでいるだけ**である。
純粋な論理カウンタなら、ピアが巨大な値を主張してもこちらのカウンタが大きくなるだけで、
`now()` が止まることも飽和することもない。

遠未来拒否の方も、attestation プールのバケット構造(§4.4)が生んでいる攻撃面への対処であり、
残るのは「嘘のフロンティアを主張する authority」= **明示的にスコープ外のビザンチン故障**。

### 3.7 例外候補: LWW

LWW-Register は「後の書込が勝つ」だが、純粋な論理カウンタにすると
「たまたま多くイベントを経験した方が勝つ」になり、ユーザーの直感と乖離する。
**ここだけは物理時間の意味論をユーザーが実際に欲しがる場所**であり、
原則との衝突を明示的に扱う必要がある(現状は暗黙)。

## 4. リーダーの存在と、それが生んでいる負債

### 4.1 この系で唯一の恒久的な選出リーダー

他は全部リーダーレス(CRDT merge / gossip / frontier 報告 / 証明書組立 / GC ゲート判定)。
制御プレーンの Raft だけが選出リーダーを持つ。
certified write の「単一ライター」も広義には調整者だが、選出ではなく書込ごとのコーディネータ。

**実装は本物の Raft**(選挙制限 / Figure 8 commit 規則 / 当選時 no-op / 投票の永続化順序 /
configuration fencing / prevote-lite)。本番配線も確認済み。Detached はテスト足場のみ。

### 4.2 採用理由が軸を外している

`architecture.md` は「スループットは重要でない(低頻度・小ログ)ため正しさ優先」と書くが、
**高遅延環境でリーダーが問題になるのはスループットではなく到達性と可用性**。
示された根拠が提起される反論に答えていない。

- 選挙タイムアウトは RTT より十分大きくなければならず、断続接続では収束しない
- `503 NOT_LEADER` は「過半数に到達できる」より強い「**リーダー個体に到達できる**」を要求する
- **ポリシーを変えたいのは障害や分断の最中**。制御プレーンが書込を拒むのはまさにその瞬間

### 4.3 表現の不正確さ

制御プレーンを単に「CP」と呼ぶのは不正確。**書込は線形化されるが読みは結果整合**
(ReadIndex も leader lease も未実装。leader lease は高スキュー環境で安全性根拠にできないため
意図的に不採用)。分断少数派で「読める」のは**古い可能性のあるローカルビューが読める**の意。

### 4.4 north star が原則と逆方向

`control-plane-scaleout.md` の到達点は Scatter 型の range 委譲 =
**1 個のリーダーが N 個になる**。文書自身が「到達点はルートの消去ではない」と明記。
「リーダーがいないのが良いところ」という原則を採るなら、north star 自体が候補から外れる。

### 4.5 Raft が実際に運んでいる荷物と、信頼の根の非対称

複製されるのは 3 つのみ — 配置ポリシー / **手動** authority 定義 / 決定的な版カウンタ。
自動生成 authority・版履歴・namespace 版そのものはノード局所の導出値で複製されない
(「同一ログ ⇒ 同一状態」は複製コアの射影についてのみ成立)。

一方 **最重要の信頼の根である Raft 投票者集合は静的 env 設定で複製されておらず**、
C3 がこれを恒久原則として固定している。合意の外にある。

### 4.6 ビザンチン耐性の非対称

制御プレーン Raft RPC の認証は共有トークンのみで、**設定時のみ**有効(未設定・空文字列は
認証なし)。メッセージ単位のノード帰属署名は無い。
**voter 1 台の侵害またはトークン漏洩で、任意の authority 定義・配置ポリシーを正規手続きで
commit できる**(followers は正当なリーダー提案として複製するので過半数の侵害は不要)。

結果、authority プレーンへの署名投資(署名検証・PoP・二枚舌検知)は実効的に迂回される —
自分の鍵を authority 集合に登録すれば certified write を正規手続きで偽造できる。
**システム全体のビザンチン耐性は制御プレーンの最弱 voter 1 台で決まる。**

## 5. 丸めが生んでいる構造的な負債

### 5.1 過半数の計算が 2 本に割れている ★

現在、過半数の判定が 2 通り並存している。

- **フロンティア集合側**: 報告を時刻順に並べて上から過半数番目を取る。グリッド不使用
- **プール側**: バケットを新しい順に走査し、書込時刻以上で人数が閾値に届く最初のバケットを探す

**述語の形が違うため答えが食い違う。** フロンティア集合側が先に certified と判定し、
プール側はまだ証明書を組めない。結果、書込は証明書なしで昇格し、**後追いで証明書を埋める
機構**(控えのキー集合、後続 tick での組み直し、署名者不在デプロイでの全走査回避条件)が
必要になっている。

証明書に書いてあるチェックポイント値と、certified 判定の実際の根拠が別物になっている。

### 5.2 遅延がバケット幅で決まる

署名済みチェックポイントは書込より「バケット幅 + 報告間隔 1 回」遅れる。
この値がそのまま証明遅延になる。

### 5.3 つまみが結合している

バケット幅は報告間隔以上でなければならない(各 authority が各バケットに最低 1 回現れないと
そのバケットで過半数が揃わない)。2 つのつまみが独立に回せない。

### 5.4 バケット構造が攻撃面を作り、上限群を要求している

区画あたり 128 チェックポイントというバケット窓が存在するため、
**遠未来バケットで窓を埋め尽くす攻撃**が可能になり、それを塞ぐために
遠未来拒否(60 秒)・「上限をスキュー許容より意図的に広く取る」論証・最古バケットの刈り取り、
という一連の機構が必要になっている。

フロンティアは単調なので、本来は authority ごとに最新 1 件で足りる情報である。

## 6. 権威定義まわりの構造的問題

### 6.1 2 つのマップが独立している

権威定義と配置ポリシーが別々の `HashMap` で、**片方だけ存在する状態が普通に作れる**。
これが以下の不具合の共通の源。

### 6.2 catch-all シードが GC を永久停止させる(D1)

起動時に全キーに一致する空接頭辞の権威定義が**手書き扱い**(自動生成フラグが false)で
種として置かれるが、**ポリシーが付いていない**。

- 自動生成でないため、ポリシー消失による刈り取りの対象にならない
- certified ポリシーが無いため、再計算での更新対象にもならない
- → **「定義はあるがポリシーが無い」状態で永久に居座る**

GC ゲートは「登録されている全 range の全 authority が報告済みか」を AND で要求するため、
**誰も報告しないこの range を待ち続け、起動直後から GC が無音で永久停止する。**
同型の停止が compaction 側にもある。

### 6.3 準備状態の判定が約 9 箇所で個別に再実装されている

「この range は稼働中か」の判定がコード内に散在し、それぞれ微妙に異なる。
`all_authority_definitions` の生アクセサが複数箇所から直接使われている。

### 6.4 エラー面が不揃い

キーから区画を解決するとき、**権威定義が無い場合とポリシーが無い場合で異なるエラー種別**が
返る(前者は PolicyDenied、後者は InvalidArgument)。

## 8. 設計プロセスと文書の問題

### 8.1 加算的になっている

`docs/design/` は 8 エージェント編成の成果物で、決定サマリが全領域で
「案 A 採用 + B から **6 点 / 12 点 / 3 点**接ぎ木」の形をしている。
**削除の圧力がかかっていない。** 特に A2 の「12 点接ぎ木」に症状が強い。

### 8.2 過剰設計の疑いが強い 2 件

**A2 Phase 2(OwnershipState)**: 第 4 の Raft 複製対象 + scope ごと epoch + 4 状態
ライフサイクル + vN 能力ラッチ + decommission API + 全証跡への per-scope epoch 刻印。

- **複雑さが複雑さを産んでいる**: strict マーカー v2 と Ownership 版 vN の混同でラッチが
  空洞化する危険が新たに生まれ、それを塞ぐピンテストがまた要る
- per-scope epoch 刻印は**実観測された障害ではなく C1 という制約文書から来ている**

**A3 Stage 2-3(交渉プロトコル本体)**: I1 が明言するとおり **v2 のバイト列は v1 と同一**なので、
買うのは「ピアあたり再起動 1 回につき JSON 再送 1 往復の削減」+ 厳格デコードのみ。
本命の理由は C4(将来のワイヤ追加)= 将来要求。
**A3 自身が案 B を「features 集合は将来要求先行(過剰設計の歯止めに抵触)」で却下**しており、
同じ物差しが自分にも当たる。

(Stage 0 の 3 重複製 fallback 統合は純減で、こちらは問題なし。)

### 8.3 記法と実行順

- 実装前に習得すべき語彙体系が大きい:
  R1-R5 / C1-C6 / D1-D10 / S1-S6 / M-4,7,12,14,16,17 / I1-I4 / T1-T7 /
  Stage 0-3 / Step1-2 / Phase 0-5
- 実行順が相互に縛られている: R-c(コミット B を先にマージ)/ D-5 直列化 /
  Step1+2 同一リリース / Phase 4 > Phase 2 / R3⇄R4 は soft
- A1 の文書重量(9 行の許可行列 + 遷移表 T1〜T7 + allowlist grep 規約 + 写像同値ピン)が
  実挙動変更 2 行に対して過大
