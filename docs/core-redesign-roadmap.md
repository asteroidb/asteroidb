### S2: メンバーシップ基盤 — 【再設計】(確信 high、規模 L)

継ぎ目の本質は「到達性シグナル(gossip ping)と安全性の母集合(データ所有メンバーシップ)の混同」。gossip registry は ping 3 連続失敗(membership.rs:100 MAX_PING_FAILURES=3 × node_runner.rs:271 ping_interval 10s + 5s timeout ≈ 30-45s)で無条件 evict する純粋な液性(liveness)機構なのに、GC 二重ゲート・Stage 2 hole-jump・push/pull 証跡の生存期間・observed relay 宛先という安全性入力に直結している。この一つの根から (a) evict が遅い方向の欠陥=dead peer 残存で GC 永久停止(受容済み、node_runner.rs:3454-3457)、(b) evict が速い方向の欠陥=D4(分断 30-45s で peer がゲート母集合から消え証跡も刈られ、hole-jump が evict された生存 peer 上の live dot を破壊)と、正反対の 2 失敗モードが同時に出ている。しかも既に Raft 投票者集合は「registry から導出すると過半数の定義が壊れる」として静的環境変数へ意図的に迂回済み(main.rs:200-231, ops-guide.md:194)で、authority 配置は第 3 の別ソース cluster_nodes(node_runner.rs:1640-1696)を使う——安全性コンシューマが増えるたび registry を回避するアドホック対応が繰り返されており、今後の research 方向(whitemap §1.2 majority-reach GC=「過半数」の分母定義、quorum-consensus.md の epoch+quorum set/lease 失効後メンバ変更)は全て「管理されたメンバーシップ epoch」を前提とするため、この継ぎ目は放置すれば欠陥を生み続ける。よって「意図的に管理されるメンバーシップ epoch 層」の導入=再設計が妥当。ただし D6 は厳密にはこの根ではなく all-or-nothing 転送証跡モデル(部分失敗で frontier 非前進、node_runner.rs:2824-2839)由来で、resumable checkpoint の局所パッチで独立に修せる。

**接地と欠陥史の対応**: ■ registry=安全性入力の実箇所: (1) C-2 GC peer ゲート: node_runner.rs:3632-3637 が sync_client.peer_registry().all_peers_owned() を母集合に gc_peer_gate_passed(3695-3705, push_acked_wall_ms を peer.addr キーで照合)。(2) Stage 2 hole-jump inbound ゲート: node_runner.rs:3516-3531 が同 registry を母集合に gc_inbound_gate_passed(3589-3599)、安全論証自体が「every registry peer has pull evidence ⇒ hole is live nowhere known」(3468-3484 doc)。(3) push evidence の生存期間: evict されると 3227-3246 で push_frontiers/push_acked_wall_ms/pull_reconciled_wall_ms/observed_last_sent が全て刈られる。(4) frontier push・observed relay 宛先: push_frontiers_to_peers(2264-2293)と sync ループの observed_pending(2460-2474)は registry の現在集合のみに送る=evict 中の生存 peer は split-view 中継の盲点。■ evict 機構: membership.rs:99-100(MAX_PING_FAILURES=3)、348-380(remove_peer で完全消去、leave/evict/分断の区別なし)、announce leave も即消去(handlers.rs:2295-2299)。■ 欠陥史との対応: D4=上記(1)(2)(3)の合成——分断 30-45s で peer が母集合から消えゲートが空虚に成立、hole-jump が当該 peer 上でのみ live の dot を跨ぎ、復帰後 floor が「stale live dots are killed/rejected by the floor on merge」(3462-3465)で恒久破壊。この根から出ている=確認。dead-peer GC 停止=同じ registry の逆方向失敗(3454-3457「DEAD PEER LEFT IN THE REGISTRY stalls collection」、ops-guide.md:570,643,1422)。D6=node_runner.rs:2817-2839(部分失敗で frontier 非前進、次周期同一 prefix 再走査)+証跡が全量走査のゼロエラー完遂にのみ付与(2810-2815, 4450-4463 evidence_valid)——根は転送プロトコルの checkpoint 欠如であり membership ではない(この根からは出ていない=否定)。■ 迂回の前例(継ぎ目が既にバグを生んだ傍証): ops-guide.md:184(hole-jump は registry peer 全量取り込みが条件と明記)、ops-guide.md:194「gossip の PeerRegistry からは導出しない(ping 失敗による自動 evict で過半数の定義が変わり選挙安全性が壊れるため)」+ main.rs:203 phantom voter 警告。■ 証跡キーの追加の皺: 証跡 map は node_id でなく peer.addr キー(3695-3705, 2440 peer_key=peer.addr)のため、gossip reconcile の update_address(membership.rs:413-415)で証跡が宙に浮き fail-closed 停止する(安全側だが停滞経路が増える)。

**再設計骨子**: ■ 捨てるもの: 「registry の現在集合=安全性の母集合」という暗黙の同一視のみ。gossip/ping(発見・RTT・topology)と MembershipClient 本体は捨てない。■ 新構造の骨子: 到達性(gossip、秒オーダで変動してよい)とデータ所有メンバーシップ(明示遷移のみ: joined → active → departing(全量 handoff 証跡確認後) → departed、各遷移で epoch 単調増加)を分離する。所有メンバーシップは既存の Raft control plane(src/control_plane、静的 voter 集合は既に稼働)に載せるのが自然で、quorum-consensus.md の前例(Aurora epoch+quorum set の非ブロッキング可逆変更、Hermes の lease 失効後のみ membership 反映、Niobe の membership だけ Paxos 直列化)と一致する。GC 二重ゲート・hole-jump・証跡 map の prune(3227-3246)は「epoch 付き所有集合のスナップショット」を母集合に取り、証跡キーは addr から node_id(+epoch)へ移す。ping evict は所有集合に触らず suspect マークと relay/同期の宛先選択にのみ影響。■ 段階移行(D1 並行実装と衝突しない): Phase 1(S-M、D4 即応)= followup-plan D4 の処方どおり「gc_retention(300s)以上の grace 付き GC 用ピア集合」を node_runner 内に追加——evict されても grace 窓内は母集合に残し証跡も刈らない。ゲート関数は純関数のまま引数の集合が変わるだけ。Phase 2(L)= Raft 経由の epoch 付き replica set と decommission 運用 API、ゲート・hole-jump・authority 再計算(cluster_nodes との三重ソースを二重に統合)を epoch スナップショット消費に切替。Phase 3= その土台上に whitemap §1.2 の majority-reach GC / stability frontier(分母=epoch 集合)を研究実装。■ D6 は本再設計に含めない: 成功バッチ末尾までの frontier checkpoint 化(node_runner.rs:2824-2839 と push_changed_keys の HLC 順維持)という局所パッチで先行修正可能。■ 検証資産への影響: ゲート系ユニットテストは純関数シグネチャ維持で無傷、membership.rs のテストも無傷。追加が必要なのは followup-plan 実証不足 2 の「evict 閾値超分断→復帰 e2e」で、これは Phase 1 の受け入れテストを兼ねる。

**壊してはいけない核**: (1) C-2 修正で確立した二重ゲートの証跡意味論そのもの——「push_acked_wall_ms はゼロエラー完遂 push の走査開始ローカル壁時計のみ」「pull-advanced peer_frontiers を push 証拠に使わない」「データ HLC physical を壁時計 mark と比較しない」(node_runner.rs:3430-3452, 3677-3691)。これは C-2 復活バグの再発防止として敵対的に検証済みの核であり、変更するのは母集合の供給源だけにする。(2) gc_peer_gate_passed / gc_inbound_gate_passed が &[PeerConfig] とマップを引数に取る純関数である構造(3589-3599, 3695-3705)——テスト資産がそのまま生きる。(3) TombstoneGc の mark-and-sweep・compaction_floor・Stage 2 の「mark 時点スナップショット以下の hole のみ跨ぐ」規律(3468-3495)。(4) Raft 投票者集合の静的設定(main.rs:200-231)——これは正しい判断であり、epoch 層導入後も投票者集合を gossip に自動追従させてはならない。(5) membership.rs の SSRF/アドレス検証群とそのテスト(45-97, 452-601)——発見・到達性レイヤとしての gossip は健全で、そのまま残す。

### S3: Certified レーンの未完 — 【再設計】(確信 high、規模 L)

継ぎ目3は「証明プレーンは完成・値プレーンは不在」という半完成状態で、D2/D3/D9 と docs 過大表明が全て同一の根(証明=authority 時計の通過のみを束縛、値は非複製)から出ている。attestation/署名/equivocation/BLS の証明機構自体は M-4/7/12/16/17 で硬化済みでバグ工場ではない。バグ工場は「certified と名乗る値がライターの単一コピーにしか存在しない」構造そのもので、値複製を後付けパッチで足すのではなく値プレーンの設計(どの store に住み、誰が複製し、証明が何を意味するか)を決め直す必要がある。「未完機能の完成」という位置づけは概ね妥当だが、完成には書き込みパス・永続化レイアウト・ステータス意味論の同時変更を要するため、実態は値プレーンの再設計である。推奨は段階案: (1) 値プレーンを eventual store に統合(相乗り)して D2/D9/二重store非整合を既存 anti-entropy で解消、(2) 統合 store の HLC vs majority frontier で status API を再定義し D3 解消、(3) 将来 Byzantine フェーズで FastPay 型の値ハッシュ ack により証明意味論を「到達性」から「値受領」へ格上げ。

### S4: push 再スタンプ + origin HLC 非搭載 — 【パッチ】(確信 high、規模 M)

「origin HLC をワイヤに載せない」は確かに M-6 ピンポン・RR ゲートの 3 条件 + poison 素通り例外・digest からの timestamps 恒久除外・5 本のローカル frontier 証拠レーン(C-2 の温床)の共通根だが、根の大半は既に閉じているか有界化されている。(1) 実害バグ(ピンポン)は RR で修正済みで RED-first 静止テスト 4 本により固定、(2) 残存コストは正しさではなく効率(1 ホップエコー、送信側 δ 差分未実装)と進化の閉塞(digest×timestamps、push でのセッション claim 不可)、(3) 現存欠陥 D1〜D10 にこの継ぎ目由来は無い。「origin frontier をワイヤに載せる再設計」のうち BP を健全化するフル版は per-delta δ-buffer(Enes 原典形)が必須で(単一 origin タグの不健全性は検証パネル 3 名の反例で確定済み)、merge/伝播コアの書き換え = XL 工数に対し得るものは有界な 1 ホップエコーの削減のみで割に合わない。安価版(v2 ワイヤ: SyncRequest に per-key HLC を追加し受信を既存の merge_remote_with_hlc 意味論へ合流)は followup-plan に互換経路検証済みで記録されており、これは足場の交換ではなく pull 側の実証済み意味論への push 側の合流 = パッチ規模。ただし v2 でも prune の片側性により per-key HLC は完全収束せず digest 制約は解けない(architecture.md が明記)ため、再設計の主張する構造的利得自体が部分的。よって裁定はパッチ: 再スタンプ足場 + RR は維持し、v2 ワイヤを唯一の追い掛けパッチとして実施(response 方向の二段デコードと note_applied→note_visible の独立レビューが前提条件)。BP/δ-buffer は否定的知見として現状維持。

### S5: ワイヤ互換の積み木 — 【再設計】(確信 high、規模 M)

継ぎ目 5 は「バグを直接生む」より「進化を抑圧し互換税を毎回徴収する」型の構造負債。永続層(WAL/snapshot)と digest レーンは明示バージョン+凍結デコードアームで健全だが、HTTP ワイヤ本体だけが無バージョンの位置依存 bincode で、互換は (a) codec.rs の残余非検証(M-14 で load-bearing 化・テストでピン留め)、(b) 旧→新 request の毎回 400+JSON 再送、(c) 旧→新 response のリクエスト丸ごと JSON 再送信(高遅延リンクで RTT 2 倍)、(d) 同一フォールバック機構の 3 重複製、という手作り積み木に依存する。この継ぎ目は既に M-6 派生「v2 ワイヤ(per-key HLC 付加)」を却下・凍結させ、M-8/M-14 で大きな互換工学コストを支払わせ、実証不足 #5(凍結旧形状デコードテスト欠落)を残した。今後も per-key HLC v2 ワイヤ・D6 resumable sync・certified 複製(D2)・PreVote(m-8 残余)と既知のワイヤ進化が最低 4 件並んでおり、税は再発し続ける。よって「ワイヤバージョン交渉層」に限定した再設計を推す。シリアライゼーション形式の置換(protobuf 等)は不要かつ有害 — digest レーンの scheme_version+scheme_ok 交渉が既にリポジトリ内の成功例であり、同じパターンを HTTP ワイヤ全体へ一般化するだけでよい。

**再設計骨子**: 捨てるもの: 「残余非検証+毎リクエスト 400 再送+response 丸ごと JSON 再送信」を恒久互換機構として使い続ける前提と、send_with_json_fallback/decode_response の 3 重複製。残すもの: bincode・全メッセージ型・JSON レーン・永続層/digest の既存バージョン体系・全テスト資産。骨子: (a) 内部ワイヤに明示バージョンを導入 — 最小案は Content-Type/Accept パラメータ(例 application/octet-stream;v=2)で、codec.rs は既に q=/charset= をパースしており(accepts_bincode codec.rs:66-105)拡張は小さい。(b) ピアごとのワイヤ能力キャッシュ — digest_sync の Unsupported キャッシュ(sync.rs:1195 周辺の 404/405 判定)と同型の一回学習に置き換え、混在期の毎リクエスト再送ストームを一回の交渉に縮約。(c) v2 フレーミングでは decode 後に消費長==全長を検査(strict decode)し、残余黙認は旧レーン(v1)専用として封印 — ピン留めテストは旧レーンのピンとして残す。(d) 3 クライアントの fallback/デコード機構を単一共有モジュール(http/codec.rs 隣接)へ統合。移行可能性: 旧 accepts_bincode はカンマ区切り各要素を独立照合するため、新ノードが v2 型を先頭に併記しても旧ノードは octet-stream にマッチして旧動作継続 — 既存のフォールバック機構を「最後の一回」だけ使う rolling upgrade で移行でき、ワイヤ断絶なし。完了後、凍結中の v2 ワイヤ(per-key HLC)・D6 resumable sync・PreVote が「末尾 append+全方向フォールバック実証」なしに v3 として追加可能になる。実証不足#5(凍結旧形状デコードテスト)はこの作業の受け入れ条件に含める。

**壊してはいけない核**: (1) 永続層のバージョン体系は現状維持 — WAL magic+version+凍結 WalRecordV1、snapshot v3/v4/v5 凍結レイアウト+migration レジストリは規律的で欠陥を出していない。(2) digest レーンの DIGEST_SCHEME_VERSION+scheme_ok 明示交渉と golden digest テスト(digest.rs:1052-1128 の scheme v2 凍結)— これは再設計の手本であり触らない。IBLT 第 3 段が来てもこの軸で進化できる。(3) bincode 自体と全メッセージ構造体定義・serde(default) 付き既存フィールド。(4) 検証資産: legacy ミラーテスト(LegacyDeltaSyncRequest 等 sync.rs:2037-2050)、WAL v1 replay テスト(wal.rs:2071-2117)、codec.rs のラウンドトリップテスト群、CRDT property テスト — いずれもペイロード意味論とレガシーレーンをピンするもので、交渉層追加では無傷。(5) 外部クライアント API の JSON 専用(codec.rs:8 の明記)。(6) M-14 の carrier 選出・observed レーン意味論(ワイヤ互換とは独立の検証済み設計)。

### S6: 無音デフォルト・握り潰しの分布 — 【パッチ】(確信 high、規模 M)

「無音デフォルト・握り潰し」は確かに D1(無音停止)・D5(無音消失)・D8(無音盲化)+ M-17 以前の無音 fence という複数欠陥を生んだ共通根だが、危険サイトは網羅列挙可能な有限個(実質 8 箇所)であり、かつコードベースは M-4 以降「counter + スロットル WARN + センチネル」の対抗規律を既に確立済み(M-6 の redundant_merge_skips、M-12 の sd2:cold、M-17 の stale_version counter が正解テンプレート)。欠けているのは旧層(hlc/crdt/eventual API/sync client/GC ゲート)への同規律の適用だけで、Result 型の全面刷新のような構造的再設計は、検証済み property テスト資産(M-6 changed 契約・M-7 digest オラクル)を危険に晒す割に追加の欠陥予防力がない。裁定は【パッチ】— ただし単発修正の羅列ではなく (1) policy 解決の単一ヘルパー化(D1 修正と同時)、(2) CRDT bool 戻り値への #[must_use] 付与(clippy -D warnings で将来の握り潰しをコンパイルエラー化)、(3) 負パス counter 5 種の一括追加、という「再発を型とCIで塞ぐパッチ群」として一度に入れる。

## 継ぎ目間 相互作用分析(6 継ぎ目の依存・波及・統合機会・研究到達順序)

前提: S1=bootstrap-namespace(再設計M) / S2=membership(再設計L) / S3=certified-lane(再設計L) / S4=push-restamp(パッチM) / S5=wire-compat(再設計M) / S6=silent-defaults(パッチM)。以下の依存主張はすべて inventory-ro スナップショットの実コードで再確認済み。

### 1. 依存グラフ(どれがどれの前提か)

**D-1: S1 と S2 は gc_gates_passed という単一関数で物理的に合流している。**
`src/runtime/node_runner.rs:3603-3640` の `gc_gates_passed` は、前半で `self.certified_api.lock() → api.namespace()` から defs を取り `unwrap_or(PolicyVersion(1))` で版を捏造(:3617-3621、S1 の根=D1)、後半で `sync_client.peer_registry()...all_peers_owned()` を母集合に peer gate を評価(:3632-3637、S2 の根=D4/dead-peer 停止)。**D1 と D4 は同一関数の左半分と右半分**である。ただし `gc_authority_gate_passed`(:3657-3675)と `gc_peer_gate_passed`(:3695-3705)は集合を引数に取る純関数なので、S1 の母集合修正(defs→RangeState::Active のみ)と S2 の母集合修正(registry→grace 付き集合)は**引数の供給側だけが変わり、互いに衝突しない**。並行作業可能、ただし受け入れテストは合同で(後述 2)。

**D-2: S3 は段階によって依存先が異なる(これが Step1 相乗り案の決定的根拠)。**
- S3 Step1/2(値プレーン統合+status 再定義)は S2 に**依存しない**: 既存 eventual anti-entropy(gossip peers 宛)に相乗りするため、authority NodeId→addr の耐久解決が不要。
- S3 Step3(FastPay 型値ハッシュ ack)のみ S2 Phase 2 に**強依存**: `AuthorityDefinition` は `authority_nodes: Vec<NodeId>` のみで addr を持たず(`src/control_plane/system_namespace.rs:22-26` 確認)、addr は evict される gossip registry にしか無い。Step3 を S2 Phase 2(Raft 複製の epoch 付き replica set)より前に着手すると、D4 と同じ「到達性を安全性に流用」を再演する。
- S3 Step2 は S1 に**弱依存**: status 再定義は「どの range が Active か」の判定を要し、admission(`certified.rs:206-231` の NoPolicy 拒否、確認済み)と同じ (def∧policy) 述語を消費する。S1 の `range_states()` が先にあれば Step2 は 8 箇所目の個別再計算を作らずに済む。

**D-3: S4 の唯一の残パッチ(v2 ワイヤ)は S5 の完了が実質前提。**
`docs/followup-plan.md:149-154`(確認済み)が明記する v2 ワイヤのブロッカー「response 方向の旧 SyncResponse 二段デコードが別途必須」は、S5 の交渉層(Content-Type v=2 + ピア能力キャッシュ + strict decode)がまさに一般解として解消するもの。S5 を先にやれば v2 ワイヤは「交渉層上の v3 メッセージ追加」に縮退し、`sync.rs:1133-1160 / 1210-1240` に既にある手作り二段デコードの**4 個目の複製を作らずに済む**。逆順(S4 先行)は S5 が削除対象とする機構を増やす逆行。

**D-4: S4 の v2 ワイヤは S3 Step2 の品質を格上げする(未指摘の相互作用)。**
S3 Step2 は「共有 store の record_change HLC vs majority_frontier」で status を判定するが、push 経路は受信側で `clock.now()` 再スタンプ(`eventual.rs:611-617`)のため、**非ライターノードの record_change HLC は origin と異なり、同一キーの status 回答がノード間で分岐する**(ライター=Certified / 非ライター=Pending が起こりうる。pull 経路は `DeltaEntry.hlc` 搭載済みで origin 採用のため片側のみ)。v2 ワイヤ(push でも origin HLC 採用)が入って初めて status 回答がクラスタ収束する。よって推奨順序は S3 Step2(ライター中心の正しさ)→ S5 → S4 v2(クラスタ収束への格上げ)。

**D-5: S2 Phase 2 と S1 は同じ control plane を触るため順序制約がある。**
S1 のシード降格は `build_bootstrap_command`(`raft/node.rs:979-1001`)の複製内容を変え、S2 Phase 2 は同じ `state_machine.rs` の Bootstrap 経路(:76-96 確認、冪等 reset-and-import)に epoch replica set コマンドを追加する。さらに S2 Phase 2 は第 3 ソース `cluster_nodes` 経由の `recalculate_authorities`(`node_runner.rs:1640-1696` 確認)を epoch 集合消費に統合する計画で、これは S1 の `range_states()` の**供給側**を差し替える作業。S1 の導出ビューが先にあれば、S2 Phase 2 は「アクセサの裏側の差し替え」で済み消費側 7 箇所に再び触らない。**順序: S1 導出ビュー → S1 シード降格 → S2 Phase 2**。

**D-6: S6 は S1/S2 の証拠チェーンに部分従属する。**
S6 の未起票欠陥 `decode_response(resp).await.ok()`(`sync.rs:929-936` 確認: 2xx ボディ不解読で error_keys 空 → `push_acked_wall_ms` 偽前進 :4414/:4444 確認)は、S2 の peer gate が消費する**証拠そのもの**の fail-open。S2 Phase 1(grace 付き集合)は母集合を広げる=この証拠への依存を強めるため、**decode 修正は S2 Phase 1 と同時か先行が必須**。一方 S6-(1)(policy 解決ヘルパー)は S1 の `range_states()` に完全に包含される(後述 3)。

### 2. 同時に触るべき組 / 触ってはいけない組

**同時に(単一レビュー文脈で):**
- **S1 導出ビュー + 進行中 D1 修正ブランチ**: D1 修正を「4 箇所目の個別整合」で終わらせず第 1 段として吸収。S6-(1) ヘルパーもここに畳む。受け入れテスト=followup-plan 実証不足 #2(本番同等シード GC 収束 e2e)。
- **S6 decode_response 修正 + S2 Phase 1**: 両方 push 証拠チェーン(C-2 核)に触る。証拠意味論「ゼロエラー完遂 push のみ」(`node_runner.rs:3677-3691`)を守る単一の敵対的レビューで。
- **S5 交渉層 + S4 v2 ワイヤ**: v2 を交渉層の初回利用例として連続実施。静止テスト 4 本(`tests/delta_sync.rs:741,828,884,1065`)無修正パスが合同の合格条件。
- **docs 訂正(D10 + user-guide.md:435 の過大表明)**: 何にも依存しない。即時・単独で。

**同時に触ってはいけない:**
- **S3 Step1(store 統合)と S4 v2 ワイヤ**: 両方 SyncRequest→merge 経路の流量・意味論を変える。共有の壊すな核(RR 3 条件 `eventual.rs:582-609`、`MergeEffects.changed` 契約)への二重変更は静止テストの失敗原因を特定不能にする。v1 ワイヤ凍結のまま Step1 を先に着地。
- **S2 Phase 2(epoch 母集合差し替え)と過半数ゲート緩和(min→k 番目統計量)**: 母集合ソース交換時は判定式不変(`gc_authority_gate_passed` の min/all をそのまま)が S2 調査の壊すな核。緩和は whitemap §1.2 の未証明白地(:49-52)であり、別の敵対的検証ステップとして分離。
- **Raft 投票者集合と epoch 層の再結合**: `main.rs:200-231` の静的設定は意図的迂回であり、S2 Phase 2 完了後も投票者集合を epoch/gossip に自動追従させない(両調査一致、恒久禁止)。
- **S1 シード降格と S2 Phase 2 の Bootstrap 変更**: 同一 Bootstrap 経路への同時変更は移行リスクの積。D-5 の順序で直列化。

### 4. research 到達のための必要順序

- **whitemap §1.2 majority-reach GC**(:49-52,123): 「過半数」の分子は frontier 集合(既存)、**分母が未定義**なのが現状。分母には (i) range ごとの authority 集合の明確な準備状態(S1: AuthorityOnly を分母に入れない定義)、(ii) epoch で管理された集合(S2 Phase 2: evict で分母が変わると過半数の意味が壊れる——静的 voter 迂回 ops-guide.md:194 と同じ理由)、(iii) 緩和時の停滞可観測性(S6 の counter 群)が前提。**S1 → S2 Phase2 → ゲート式緩和**の順以外では ⚔T1(GC↔fork 復旧、whitemap:109)の resurrection リスクを検証不能。
- **stability frontier**(delta-crdt.md:59,83: causal stability は fixed membership + 全レプリカ timestamp 発行前提、HLC での等価性未証明): 分母に epoch 集合(S2 Phase 2)が必須なのに加え、**per-key origin HLC のレプリカ間収束(S4 v2 ワイヤ)が無いと per-key stability 判定がそもそも比較不能**(再スタンプ ts は architecture.md:395-399 の通りローカル採番)。順序: S5 → S4 v2 → (S2 Phase 2 と合流) → stability frontier。
- **CT gossip**(anti-entropy.md:655「署名付き frontier root を anti-entropy に相乗り」): 相乗り先は既存の observed relay レーン(`node_runner.rs:2460-2474` 確認、M-14 carrier)。前提は (i) S2 Phase 1 — relay 宛先が registry 現在集合のみだと evict 中の生存 peer が split-view 検知の盲点(D4 調査の指摘)で、検知網としては致命的、(ii) S5 — STH 相当の新メッセージ追加をフォールバック工学なしで、(iii) S6 の D8 counter — equivocation store の LRU 無音 evict は検知網の無音盲化。

**統合実行順(全体)**: ①即時並行: docs 訂正 / S6 パッチ群(decode 含む) / D6 ローカルパッチ → ② S1 導出ビュー(D1 ブランチ吸収)∥ S2 Phase 1(+decode 修正合流) → ③ S1 シード降格 / S5 交渉層 → ④ S3 Step1+2(S1 後)/ S4 v2(S5 後、S3 Step2 を格上げ) → ⑤ S2 Phase 2(control plane 安定後、三重ソース統合) → ⑥ 研究層: majority ゲート緩和・stability frontier・CT gossip(⑤の epoch 集合を共通分母として)。S3 Step3 は⑤完了後のみ着手可。

### 1. 総括

**core rewrite は不要。継ぎ目の再設計 4 件(S1/S2/S3/S5)+規律パッチ群(S4/S6)で十分である。** 根拠: 欠陥史 D1〜D10・M 群を実コードに逆写像すると、全てが (a) namespace 準備状態の消費側分岐(S1: D1, M-4 経路, M-12 派生, check_compaction 潜在)、(b) 到達性と所有母集合の混同(S2: D4, dead-peer 停止)、(c) certified 値プレーンの不在(S3: D2/D3/D9/D10)、(d) 無バージョンワイヤの互換税(S5)、(e) 無音デフォルト(S6: D5/D8)の 5 根に収束し、一方で merge/CRDT 意味論(MergeEffects.changed 契約)、C-2 二重ゲートの判定式、WAL/snapshot のバージョン体系、証明プレーン(attestation/equivocation/BLS)、RR 再スタンプゲートといった**コアの計算意味論からは欠陥が出ていない**。バグ工場は「消費側が一次状態を各自再解釈する継ぎ目」に限局しており、各継ぎ目は判定式・純関数シグネチャ・永続形式を不変に保ったまま供給側だけ差し替えられる(gc_authority_gate_passed / gc_peer_gate_passed が集合を引数に取る純関数である事実 `node_runner.rs:3641-3705` がその移行可能性の構造的証拠)。よって全面書き直しは検証済み資産(property テスト、静止テスト 4 本、golden digest、C-2 安全論証)を無価値化するだけで、得るものがない。

### 3. 【パッチ】D1〜D10 の帰属

**再設計に吸収されるもの:**
- **D1** → R1 に吸収(進行中ブランチは第 1 段として取り込み、check_compaction:3325-3345 の未収載同型欠陥と resolve_scope エラー面も同時に閉じる)。

- **D2, D9** → R4 Step1(store 統合で D9 は eventual 同等保護に格下げ、M-7 digest が certified 値を初めて内容束縛)。
- **D3** → R4 Step2(status を共有 store HLC vs majority frontier で再定義、NotTracked 追加、cache 無効化を store フックへ)。
- **S4 v2 ワイヤ(per-key HLC)** → R3 の上の v3 メッセージ追加に縮退(手作り二段デコード 4 個目を作らない)。

**独立パッチのまま実施するもの:**
- **D5**: ClockSkew counter + `LwwRegister::set` 戻り値の STALE 化(eventual.rs:554,663)。merge を止める方向の変更は禁止。
- **D6**: 成功バッチ末尾までの frontier checkpoint(node_runner.rs:2824-2839)。送信側ローカル変更でワイヤ非依存 = R3 を待たない。
- **D8**: equivocation LRU eviction counter + 上限設定化(equivocation.rs:337-366)。eviction 廃止ではない。
- **D10 + docs 過大表明訂正**: 即時・単独。何にも依存しない。

### 4. 【現状維持】と受容理由

- **push 再スタンプ足場 + RR ゲート(S4 本体)**: 実害(M-6 ピンポン)は修正済みで静止テスト 4 本(tests/delta_sync.rs:741,828,884,1065)が固定。残余は 1 ホップエコーという有界な効率コストのみで、健全化フル版(per-delta δ-buffer)は merge コア書き換え XL。高遅延・分断という製品前提では帯域よりも意味論の安定が優先であり、割に合わない。**単一 origin タグの再導入は反例 3 件で恒久禁止**(followup-plan.md:141-144)。
- **Raft 投票者集合の静的設定**(main.rs:200-231): gossip 導出は過半数定義を壊す — 単一クラスタ・CFT 前提での意図的設計。epoch 層導入後も維持。
- **C-2 二重ゲートの判定式**(node_runner.rs:3657-3705)、**attestation 版ウィンドウ**、**fail-closed 揮発性**(再起動で Certified→Pending)、**WAL poison 順序不変条件**、**format_version unwrap_or(1)**(凍結 decode の一部)、**equivocation の eviction-not-rejection 設計**: いずれも敵対的検証済みか文書化された既定であり、変更は安全論証の再証明コストが利得を超過。
- **外部 API の JSON 専用**(codec.rs:8)と**永続層バージョン体系**: 欠陥を出していない規律的設計。

### 5. 実行順序(フェーズ)

- **Phase 0(即時・全並行)**: docs 訂正(D10 + user-guide 保証範囲)/ S6 パッチ群(D5・D8 counter、#[must_use]、decode_response — ただし decode は Phase 1b と同一レビュー)/ D6 checkpoint。**D1 実装ブランチとは無衝突**(触るファイル領域が分離)。
- **Phase 1a**: R1 導出ビュー。**進行中の D1 ブランチをそのまま第 1 段として吸収** — gc ゲートの母集合修正を range_states() 経由に置き、check_compaction も同時に切替。受け入れ=実証不足 #2 前半(本番同等シード GC 収束 e2e)。
- **Phase 1b(1a と並行可)**: R5 Phase 1(grace 付き GC ピア集合)+ decode_response 修正。両者は gc_gates_passed の左半分/右半分だが純関数の引数供給側のみで衝突しない。受け入れ=実証不足 #2 後半(分断→復帰 e2e)。
- **Phase 2**: R2 シード降格 / R3 交渉層(並行可)。R3 の受け入れに実証不足 #5 を内包。
- **Phase 3**: R4 Step1+2(R1 後、v1 ワイヤ凍結のまま着地)→ その後 S4 v2 ワイヤ(R3 後、v3 メッセージとして)。順序理由: v2 ワイヤが入って初めて非ライターノードの record_change HLC が origin 収束し、Step2 の status 回答がクラスタ収束する(D-4)。**Step1 と v2 の同時変更は禁止**(共有の壊すな核への二重変更)。
- **Phase 4**: R5 Phase 2(epoch replica set、三重ソース統合、decommission API)。R1/R2 で Bootstrap 経路が安定した後。母集合ソース交換時は判定式(min/all)不変。

### 6. リスク と歯止め

1. **検証資産の毀損**: 最大リスクは R4 Step1 が MergeEffects.changed 契約・RR 3 条件・WAL merge-dominance に触れて property/静止テストを壊すこと。歯止め: 「壊すな核」を各フェーズの**無修正パス必須テスト**として明文化(静止テスト 4 本・golden digest・property_quorum・gc ゲート単体は、シグネチャ機械追随以外の変更を PR で拒否)。
2. **移行不能**: R2(シード)と R5 Phase 2(Bootstrap)の同時変更、R4 の certified WAL 一方向再生。歯止め: D-5 の直列化順守、R4 移行は merge-dominant post-state 不変条件を正当性根拠とする移行テストを完了条件に、R3 は旧 accepts_bincode のカンマ独立照合による rolling upgrade 実証を先に。
3. **過剰設計**: R5 Phase 2 の epoch 層と R3 交渉層は「将来の税」への前払いであり、単一クラスタ MVP には重い誘惑がある。歯止め: Phase 2/4 は各々の直接欠陥(実証不足 #5、dead-peer runbook 依存)を受け入れ条件に持ち、研究層(Phase 5)の要求だけを理由にした着手を禁止。protobuf 化・δ-buffer・ゲート式緩和と epoch 差し替えの同時実施は明示的に不採用/分離。
4. **並行 D1 ブランチとの衝突**: D1 修正が「4 箇所目の個別整合」で main に入った場合、R1 は即座にそれを導出ビューへ畳む(挙動同一のリファクタ)ことで手戻りを Phase 1a 内に閉じる。
5. **無音停止の再発**: 全フェーズで fail-closed 方向は維持しつつ、gates_passed=false への counter/WARN(S6 規律テンプレート: M-6/M-12/M-17 型)を各ゲート変更に必ず同梱 — 「安全だが無音」を「安全かつ可観測」にするのが本計画の通奏低音であり、判定緩和は Phase 5 の敵対的検証ステップまで一切行わない。
